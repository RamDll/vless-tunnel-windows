# vless-tunnel для Windows — план реализации

Задача для агента. Сделать нативный клиент для Windows 10/11 по образцу
Linux-версии [RamDll/vless-tunnel](https://github.com/RamDll/vless-tunnel)
(эталон — v1.2.9). Переносится **поведение**, а не код: bash, iptables,
systemd и sudoers в Windows заменяются аналогами ниже.

Главное требование владельца: ссылки с post-quantum параметрами
(`encryption=mlkem768x25519plus…`, REALITY `pqv`) должны работать так же,
как на Linux и на роутере. Из-за них чужие клиенты не подходят.

---

## 1. Стек и решения

| Что | Решение |
|---|---|
| Язык | C#, **.NET 10 (LTS)**. .NET 8 не брать: поддержка заканчивается в ноябре 2026 |
| Цели | Windows 10 22H2 x64 и Windows 11 x64. ARM64 позже |
| Публикация | self-contained, `PublishSingleFile`, без требования ставить рантайм |
| Ядро | официальный `xray.exe` + `wintun.dll` из релиза XTLS/Xray-core (win-64 zip), версия закреплена, sha256 сверяется |
| Перехват | TUN-инбаунд Xray (Wintun) + маршруты, которые ставит служба |
| Привилегии | Windows-служба от LocalSystem; GUI и CLI без UAC, через named pipe |
| Установщик | Inno Setup (`.exe`), собирается в GitHub Actions (`windows-latest`) |
| GUI | WinForms: значок в трее + главное окно |

Не делаем (сознательно):
- legacy-транспорты `type=quic` / `type=http` (ядро v1.8.24): в нём нет TUN-инбаунда. Такая ссылка → понятная ошибка;
- режим шлюза для других устройств LAN;
- выборочную маршрутизацию по спискам доменов (возможно, позже: на Linux её тоже нет, это полный туннель);
- Windows 7/8.

```

  VlessTunnel.Core/      разбор ссылки, сборка config.json, модели, общие константы
  VlessTunnel.Service/   служба: Xray, TUN, маршруты, kill-switch, DNS, watchdog, IPC-сервер
  VlessTunnel.Cli/       vless-tunnel.exe — команды через IPC
  VlessTunnel.Tray/      трей + окно, клиент IPC
  VlessTunnel.Native/    P/Invoke: IP Helper (iphlpapi), WFP (fwpuclnt)
tests/
  VlessTunnel.Core.Tests/   юнит-тесты + golden-тесты паритета с Linux
  parity/                   ссылки и эталонные JSON из Linux-бэкенда
installer/
  vless-tunnel.iss
.github/workflows/
  build.yml                 сборка, тесты, установщик, релиз по тегу
```

Пути на машине:

| Что | Где |
|---|---|
| Программа | `%ProgramFiles%\vless-tunnel\` (exe, xray.exe, wintun.dll) |
| Конфиг и ссылка | `%ProgramData%\vless-tunnel\` — ACL только SYSTEM + Administrators (в ссылке секретный UUID) |
| Сгенерированный config.json | там же, пересобирается при каждом старте |
| Логи | `%ProgramData%\vless-tunnel\logs\` с ротацией + Event Log для службы |

## 3. Архитектура

### 3.1 Разбор ссылки и config.json (Core)

Портировать Python-бэкенд из `vless-tunnel.sh` (функции `parse`/`make`,
примерно строки 290–760) **один в один**:

- транспорты: `tcp`/`raw`, `ws`, `grpc` (+`mode=multi`), `httpupgrade`, `xhttp`/`splithttp` (+`mode`, `extra` как JSON), `kcp` без header/seed;
- REALITY: `pbk`, `sid`, `spx`, `fp`, **`pqv` → `mldsa65Verify`**;
- TLS: `sni`, `fp`, `alpn`, `ech`; `allowInsecure` → получить отпечаток сертификата и прописать `pinnedPeerCertSha256` (как `cert-pin` на Linux);
- **`encryption=`** передаётся в `users[].encryption` без изменений;
- `flow=xtls-rprx-vision` → клиентский `xtls-rprx-vision-udp443` (опция отключения);
- IPv6-хост в `[...]`, ссылка без схемы, многострочная вставка с разрывами.

Отличия от Linux в config.json:
- инбаунд `tun` вместо `dokodemo-door` + TPROXY;
- SOCKS5 `127.0.0.1:10808` (с UDP) и HTTP `127.0.0.1:10809` — как на Linux;
- **адрес сервера в `vnext` — уже разрешённый IP** (см. 3.2), SNI/Host остаются доменом;
- правило `port 53 → dns-out`, DNS Xray — DoH через туннель;
- приватные сети → `direct` (опция `--proxy-lan` отключает).

**Паритет обязателен** (порядок работы — 5.7). Golden-тесты: набор ссылок (включая PQ, REALITY+pqv,
XHTTP+extra, vision, IPv6-хост, битые ссылки) прогоняется через Linux-бэкенд
(`vless-tunnel.sh`, подкоманда `make`), эталонные JSON коммитятся в
`tests/parity/`. C#-сборщик должен давать тот же outbound-блок байт в байт
(после нормализации JSON). Инбаунды сравниваются отдельно.

### 3.2 Перехват трафика и петля (Service)

Встроенный TUN Xray только поднимает адаптер. Адреса, маршруты и правила
делает ОС, то есть служба. Индекс интерфейса меняется при каждом запуске
Xray, поэтому ищем его заново каждый раз.

Порядок старта:
1. **Bootstrap-резолв** домена сервера самой службой (системный резолвер, до поднятия TUN). IP подставляется в config.json. Прямой DNS-исходящий Xray для bootstrap не нужен.
2. Запомнить текущий физический интерфейс и шлюз по умолчанию (`GetBestRoute2`).
3. Запустить `xray.exe` (Job Object: при смерти службы умирает и Xray).
4. Дождаться адаптера (`GetAdaptersAddresses`, по имени из конфига), таймаут.
5. Назначить адрес TUN (`CreateUnicastIpAddressEntry`), например `172.19.0.1/30`; для IPv6 — ULA из `fd00::/8` (без маршрутизируемого адреса IPv6 через TUN не пойдёт).
6. Маршруты (`CreateIpForwardEntry2`):
   - хост-маршрут до IP сервера через физический шлюз — **это и есть защита от петли** для proxy-исходящего;
   - `0.0.0.0/1` и `128.0.0.0/1` через TUN (не трогаем штатный default route);
   - IPv6: `::/1` и `8000::/1` через TUN, либо блок IPv6 при `--block-ipv6`;
   - приватные сети остаются на физическом интерфейсе (более специфичные маршруты выигрывают).
7. DNS: DNS-сервер адаптера TUN = адрес внутри TUN, низкая метрика TUN.
8. Включить kill-switch (3.3).

Отслеживать `NotifyRouteChange2` / `NotifyIpInterfaceChange` (смена Wi-Fi,
переподключение кабеля, сон): пересчитать физический шлюз и переставить
хост-маршрут до сервера. Периодически перерезолвить домен сервера; при
смене IP — перезапуск.

Остановка — строго в обратном порядке. Все созданные маршруты и фильтры
помечаются и снимаются по метке, не «по памяти процесса».

### 3.3 Kill-switch (обязателен)

На Linux kill-switch получается «по построению». **На Windows — нет:** если
Xray упал, адаптер TUN исчезает вместе с маршрутами, и трафик молча уходит
напрямую. Поэтому kill-switch через WFP — часть MVP, а не опция.

WFP, свой provider + sublayer с высоким весом, **постоянные** (не dynamic)
фильтры, чтобы пережить падение службы:
- разрешить: `xray.exe` (по app id), интерфейс TUN, loopback, DHCP, приватные сети (если не `--proxy-lan`);
- запретить: всё остальное исходящее, IPv4 и IPv6;
- DNS-утечки: запретить порт 53 на всех интерфейсах, кроме TUN (Windows параллельно шлёт DNS во все интерфейсы).

Снимаются фильтры только явным `off` или `uninstall`. `doctor` должен
уметь их найти и снять («аварийный выключатель» на случай поломки).

### 3.4 IPC и права (аналог sudoers)

Named pipe `\\.\pipe\vless-tunnel`, ACL: SYSTEM, Administrators и
пользователь, указанный при установке (аналог `--allow-user`). Протокол —
JSON-строки: запрос/ответ + **подписка на события** (смена состояния). Трей
не опрашивает службу по таймеру (урок Linux-версии, где опрос раз в 5 с
давал сотни вызовов).

### 3.5 CLI (`vless-tunnel.exe`)

Те же команды, что на Linux, где применимо:

```
on | off | toggle | restart
status [--json]
test            HTTP, SOCKS5, прозрачный TCP, UDP/QUIC, DNS (включая проверку утечки)
logs [--lines N]
set-link [--stdin]
autostart on|off
update-core     скачать релиз Xray, сверить .dgst, откат при неудаче
doctor          окружение + вердикт + снятие зависших WFP-фильтров
ensure          переставить маршруты/фильтры
uninstall [--keep-config]
```

Таймауты клиента IPC должны быть **больше** худшего пути команды в службе
(урок Linux: `toggle` с таймаутом 30 с при пути `on` > 31 с).

### 3.6 Трей и окно

- значок: вкл / выкл / неизвестно (иконки из `packaging/icons` Linux-версии);
- меню: включить/выключить, статус, вставить ссылку, логи, выход;
- окно: ссылка (поле скрывает UUID), статус, кнопка «Проверить», журнал;
- автозапуск трея — ярлык в Startup для пользователя;
- ошибки показывают и stdout, и stderr (урок Linux: `out or err` прятал stderr).

### 3.7 Установщик (аналог .deb)

- ставит файлы, регистрирует службу (автозапуск по опции), ярлыки, трей;
- **обновление поверх**: остановить службу → заменить файлы → запустить; конфиг сохраняется;
- один путь к бинарнику, никаких копий (урок Linux: дубль `/usr/bin` и `/usr/local/bin`);
- `uninstall` из CLI не удаляет файлы, принадлежащие установщику, а только сбрасывает настройку; полное удаление — через «Программы и компоненты»;
- удаление снимает службу, маршруты и WFP-фильтры;
- версия Xray и wintun зашиты в сборку, sha256 проверяется в CI.

### 3.8 Подпись и доверие (самоподписанный сертификат)

Порядок на машине пользователя:
1. `trust.ps1` (один раз, от администратора): сверяет отпечаток `vless-tunnel.cer` с зашитым в скрипт, ставит сертификат в `LocalMachine\Root` и `LocalMachine\TrustedPublisher`, снимает метку «из интернета» (`Unblock-File`) с установщика и запускает его.
2. Установщик: установка или обновление поверх. Повторно `trust.ps1` не нужен.
3. Удаление через «Программы и компоненты» убирает всё, включая сертификат; настройки — по вопросу (см. ниже).

Сертификат: `New-SelfSignedCertificate -Type CodeSigningCert` (только подпись
кода). `.pfx` хранится только в секретах GitHub Actions и в офлайн-копии,
никогда не в репозитории. Подписываются все свои `.exe` и установщик
(директива `SignTool` в Inno Setup, включая деинсталлятор), всегда с меткой
времени (`/tr … /td SHA256`).

Деинсталлятор (Inno Setup):

```ini
[UninstallRun]
; настройки удаляет сам деинсталлятор по ответу пользователя, CLI их не трогает
Filename: "{app}\vless-tunnel.exe"; Parameters: "uninstall --keep-config"; Flags: runhidden waituntilterminated; RunOnceId: "Purge"
Filename: "{sys}\certutil.exe"; Parameters: "-delstore Root <THUMBPRINT>"; Flags: runhidden; RunOnceId: "DelRoot"
Filename: "{sys}\certutil.exe"; Parameters: "-delstore TrustedPublisher <THUMBPRINT>"; Flags: runhidden; RunOnceId: "DelTP"

[UninstallDelete]
; логи удаляются всегда
Type: filesandordirs; Name: "{commonappdata}\vless-tunnel\logs"

[Code]
var
  DeleteSettings: Boolean;

procedure CurUninstallStepChanged(CurUninstallStep: TUninstallStep);
begin
  case CurUninstallStep of
    usUninstall:
      begin
        { тихое удаление (/SILENT, /VERYSILENT) настройки сохраняет }
        DeleteSettings := False;
        if not UninstallSilent() then
          DeleteSettings := MsgBox(
            'Удалить настройки vless-tunnel (ссылку на сервер и параметры)?' + #13#10 + #13#10 +
            'Нет — настройки останутся и подхватятся при следующей установке.',
            mbConfirmation, MB_YESNO or MB_DEFBUTTON2) = IDYES;
      end;
    usPostUninstall:
      if DeleteSettings then
        DelTree(ExpandConstant('{commonappdata}\vless-tunnel'), True, True, True);
  end;
end;
```

Требования:
- вопрос задаётся после подтверждения удаления и до снятия файлов; по умолчанию выбран «Нет»;
- обновление поверх деинсталлятор не запускает — сертификат и настройки не трогаются; обновление через «удалить → поставить» не делать;
- при установке служба подхватывает существующий `%ProgramData%\vless-tunnel`, если он остался;
- один сертификат — один проект: удаление снимает доверие со всего, что им подписано;
- при смене сертификата (истёк срок) — новый `trust.ps1` с новым отпечатком; старые сборки остаются валидными благодаря метке времени.

Известное: даже подписанный файл, скачанный из интернета, SmartScreen может
показывать с предупреждением (проверка по репутации), поэтому `trust.ps1`
снимает метку `Unblock-File`. Прокси-клиенты иногда ложно ловит антивирус.

### 3.9 Эксплуатация: то, что легко упустить

**Аварийное восстановление сети.** Постоянные WFP-фильтры переживают всё,
в том числе ручное удаление папки программы. Если `vless-tunnel.exe` уже нет,
`doctor` не запустить, и машина остаётся без интернета. Поэтому:
- фильтры создаются с фиксированным GUID провайдера и sublayer (константы в Core);
- отдельный самодостаточный `rescue.ps1` (P/Invoke через `Add-Type`, без зависимостей от программы) снимает всё по этим GUID; лежит в репозитории, ссылка — в README и в меню «Пуск»;
- ярлык «Аварийно отключить vless-tunnel» в меню «Пуск».
Альтернатива WFP — правила брандмауэра Windows (снимаются штатным
`Remove-NetFirewallRule`), но они не работают, если сторонний антивирус
подменил брандмауэр. ~~Выбор сделать на этапе 0.~~ Решено на этапе 0б:
**WFP** — переживает замену брандмауэра антивирусом и падение службы
(постоянные фильтры), обычные правила брандмауэра — нет. Подробности и
обоснование — `docs/spike.md`.

**Captive portal** (Wi-Fi в гостинице, кафе). Kill-switch не пустит на
страницу входа. Нужна команда/пункт трея «Пустить на 5 минут напрямую»:
временно снимает блокировку, по таймеру возвращает, туннель не включён.

**Обновление поверх.** Файлы заняты работающими службой и треем. В
`PrepareToInstall` (Inno Setup) остановить службу и закрыть трей всех
пользователей, после установки запустить обратно. Kill-switch на время
обновления остаётся включённым, если туннель был включён.

**Обновление программы (`self-update`).** Проверка релизов на GitHub,
скачивание установщика, сверка sha256 **и** отпечатка подписи с зашитым,
запуск установщика тихо (`/VERYSILENT` — настройки сохраняются, см. 3.8).

**Смена сертификата.** `trust.ps1` содержит список старых отпечатков и
удаляет их из `Root`/`TrustedPublisher` при установке нового. Деинсталлятор
удаляет текущий и все старые.

**Запуск `trust.ps1`.** ~~Скачанный `.ps1` сам помечен «из интернета», а
политика выполнения по умолчанию запрещает скрипты. Нужна обёртка
`install.cmd`~~ — сделано и проверено живьём (см. «Статус» ниже):
`installer/install.cmd` сам проверяет права администратора, при
необходимости просит их через UAC (`Start-Process -Verb RunAs`) и уже
из повышенного процесса вызывает `powershell -ExecutionPolicy Bypass
-File trust.ps1` — реальный сценарий "скачал → дважды кликнул".

**Кодировка.** Windows PowerShell 5.1 читает `.ps1` без BOM как ANSI —
кириллица в сообщениях превратится в мусор. Все `.ps1` — **UTF-8 с BOM**
(проверка в CI). CLI выставляет `Console.OutputEncoding = UTF8`.

**Секреты в выводе.** UUID и ключи не печатаются в логах, `status`, `doctor`
и окне (маскировать). Конфиг-директория с ACL (3.2 / раздел 2).

**Устойчивость службы.** Действия при сбое (`sc failure`): перезапуск
через 5 с, 30 с, 60 с. Xray в Job Object. После сна и гибернации — полная
проверка маршрутов и адаптера, не только по уведомлениям.

**Время.** REALITY и TLS ломаются при сбитых часах (часто в виртуалках).
`doctor` сверяет время (NTP или заголовок `Date` через туннель) и
предупреждает.

**MTU.** TLS + XHTTP добавляют накладные расходы; MTU TUN 1500 может давать
фрагментацию и «висящие» сайты. Подобрать значение на этапе 0 (ориентир
1400), сделать опцией.

**Совместимость** (аналог раздела в Linux README). Проверить и описать:
другой VPN/TUN (v2rayN, WireGuard, OpenVPN), WSL2, Hyper-V, Docker Desktop
(их трафик идёт через NAT хоста — туннелируется ли и не режет ли его
kill-switch), сторонний антивирус с собственным брандмауэром.

**Лицензии.** `THIRD_PARTY_LICENSES/` как в Linux-репозитории: Xray-core
(MPL-2.0), Wintun (лицензия на готовые бинарники), .NET-зависимости.
Установщик кладёт их в `{app}`.

**Windows 10.** Плановая поддержка закончилась в октябре 2025 года —
основной целью считать и Windows 11, тестировать на обеих.

## 4. Этапы и критерии приёмки

Каждый этап — отдельный PR. Тестирование — на стенде из раздела 5;
опасные тесты — только через `with-rescue.sh`.

**Этап 0а. Стенд.** Виртуалка `vt-win10` создаётся скриптом без участия человека; SSH по ключу и guest agent работают; снимок `clean` есть; `rescue.ps1`, `run-test.ps1`, `with-rescue.sh` готовы; цепочка спасения проверена: намеренно отрезанная сеть возвращается через guest agent, а при «мёртвом» guest agent — откатом снимка.

**Этап 0б. Спайк (без C#, PowerShell).** Это ворота для всего остального. Все эксперименты — через `with-rescue.sh`.
- `xray.exe` + `wintun.dll` + TUN-инбаунд поднимают адаптер;
- ручные маршруты по 3.2 → трафик идёт через сервер, петли нет;
- тестовая ссылка с PQ-параметрами работает;
- проверить IPv6 через TUN с ULA-адресом;
- проверить, как ведёт себя система при `taskkill` Xray (подтвердить утечку без kill-switch);
- выбрать механизм kill-switch: WFP или правила брандмауэра (3.9), проверить способ аварийного снятия;
- подобрать MTU TUN;
- проверить сон/гибернацию и смену Wi-Fi ↔ кабель.
Результат — `docs/spike.md` с командами и выводами.

**Этап 1. Core + тесты.** Все golden-тесты паритета зелёные, битые ссылки дают понятные ошибки.

**Этап 2. Служба: Xray, TUN, маршруты.** `on`/`off` через временный отладочный вход; переключение Wi-Fi ↔ кабель не рвёт туннель надолго; после `off` таблица маршрутов как до `on`.

**Этап 3. Kill-switch и DNS.** `taskkill /f xray.exe` → интернета нет, пока туннель не поднимется; утечек DNS нет (проверка dnsleaktest-подобным запросом и захватом трафика на физическом интерфейсе); `doctor` снимает фильтры.

**Этап 4. IPC + CLI.** Все команды из 3.5; пользователь без прав администратора управляет туннелем; чужой пользователь — нет.

**Этап 5. Трей и окно.** Состояние обновляется по событиям, без опроса.

**Этап 6. Установщик и CI.** Чистая установка через `trust.ps1`, обновление поверх (настройки и сертификат на месте), удаление с ответом «Да» и «Нет» и тихое удаление — на свежем снимке виртуалки; после удаления сертификата нет в `Root` и `TrustedPublisher`. Релиз по тегу выкладывает `.exe` и `sha256`.

**Этап 7. Сервис-команды.** `test`, `doctor` (включая проверку времени), `update-core` с откатом, `self-update` со сверкой подписи, режим captive portal, `rescue.ps1` снимает фильтры на машине без установленной программы, логи с ротацией, секреты не попадают в вывод.

## 5. Стенд: агент на Ubuntu, Windows в виртуалке

Агент работает на хосте с Ubuntu и сам создаёт и ведёт тестовую виртуалку
Windows (KVM/libvirt). Ключевое свойство: **сеть агента от тестов не
зависит.** Сломанные маршруты или kill-switch отрезают только виртуалку, а
агент снаружи всегда может её спасти или откатить.

### 5.1 Что делает владелец (один раз)

У агента есть passwordless sudo на хосте (`NOPASSWD:ALL`, настроено владельцем
через `/etc/sudoers.d/`, см. 5.8) — установку пакетов, группы и проверку
`virsh` агент теперь выполняет сам:

```sh
egrep -c '(vmx|svm)' /proc/cpuinfo        # > 0, виртуализация включена в BIOS
sudo apt install qemu-kvm libvirt-daemon-system virtinst genisoimage ovmf swtpm
sudo usermod -aG libvirt,kvm $USER        # затем перелогиниться
virsh -c qemu:///system list              # должно работать без sudo
```

Владелец вручную делает только то, что требует браузера/интерактивного входа
или является его личным решением:

- скачивает ISO Windows 10 22H2 x64 с сайта Microsoft и кладёт в `~/vm-iso/win10.iso` (страница Microsoft требует ручных шагов, автоматически не скачивается);
- ставит .NET 10 SDK на хост (или поручает агенту через `dotnet-install.sh` — на усмотрение);
- проверяет, не заворачивает ли Linux-клиент vless-tunnel на хосте трафик виртуалки (NAT через `virbr0`) в свой туннель. Если заворачивает — отключить на время тестов или учитывать «туннель в туннеле» при оценке результатов. Записать вывод в раздел «Статус».

### 5.2 Параметры виртуалки

| Что | Значение |
|---|---|
| Имя | `vt-win10` |
| ОС | Windows 10 22H2 x64 (Windows 11 — позже, отдельной машиной) |
| Прошивка | BIOS (SeaBIOS) — ради внутренних снимков qcow2; UEFI + TPM нужны только для Windows 11 и усложняют снимки |
| Ресурсы | 4 vCPU, 8 ГБ RAM, диск qcow2 64 ГБ |
| Сеть (тестируемая) | libvirt `default` (NAT, `virbr0`) — то, что ломают сетевые тесты |
| Сеть (управляющая) | libvirt `vt-mgmt` (host-only, `virbr-vtmgmt`, 10.77.77.0/24, без forward) — только SSH, тесты её не трогают (стенд, п.1) |
| Драйверы и guest agent | ISO virtio-win (агент скачивает сам с fedorapeople.org, сверяет контрольную сумму) |
| Установка | без участия человека: `autounattend.xml` на отдельном ISO |

Секреты стенда (пароль администратора виртуалки, SSH-ключ) — в
`~/.config/vless-tunnel-dev/`, не в репозитории. Пароль генерируется при
создании.

`autounattend.xml` и скрипт первого входа (`setup-guest.ps1`) должны:
- создать локальную учётку администратора; автологин — постоянный (по решению владельца: это стенд для разработки, а не конечный продукт, вводить пароль на консоли каждый раз неудобно). Технически это ещё и единственный работающий способ запустить `setup-guest.ps1` без участия человека в этом образе: `Microsoft-Windows-Deployment`/`RunSynchronousCommand` не поддерживается этой сборкой Windows ни в `specialize`, ни в `oobeSystem` (проверено эмпирически через `setupact.log`), поэтому используется `FirstLogonCommands`, а для него нужен хотя бы один вход;
- поставить драйверы virtio и **qemu-guest-agent** с ISO virtio-win;
- включить **OpenSSH Server** (слушает только на адаптере `vt-mgmt`, стенд п.1), PowerShell как оболочку по умолчанию, вход по ключу (`administrators_authorized_keys` с правильным ACL);
- отключить сон и гибернацию (иначе автоматические тесты будут прерываться простоем) — но **не** Windows Update: владелец настоял, что стенд должен вести себя как обычная машина пользователя, иначе часть реальных проблем (обновление посреди теста, перезагрузка, столкновение с туннелем) просто не всплывёт до релиза;
- исключить `C:\dev` из проверки Defender (только эта папка со скриптами стенда, не сам vless-tunnel — тот ставится в `%ProgramFiles%\vless-tunnel\` и остаётся под обычной проверкой антивируса, как и должно быть);
- создать `C:\dev\{logs,secrets,bin}`;
- в конце выключить машину — это сигнал хосту, что установка завершена.

### 5.3 Файлы стенда в репозитории

```
vm/
  create-vm.sh          создать vt-win10 с нуля (идемпотентно: есть — не трогать)
  vt-mgmt-network.xml   определение host-only сети vt-mgmt (стенд, п.1)
  vt-test2-network.xml  определение NAT-сети vt-test2 для живых тестов смены сети (ревью п.22)
  autounattend.xml      шаблон, пароль и ключ подставляются при сборке ISO
  setup-guest.ps1       первичная настройка Windows
  vmctl.sh              ssh | scp | exec (через guest agent) | ip | test-ip | snapshot | revert | rescue | status
  with-rescue.sh        обёртка опасного теста (5.5), синхронизирует исходники (5.6/п.3)
  guest-build.ps1       сборка (dotnet publish + ISCC) целиком внутри гостя (стенд, п.3)
tests/vm/scenarios/
  acl-config-dir.ps1              пример сценария (5.5/п.2) — ACL через Get-Acl/SID
  break-service-killswitch.ps1    пример сценария (5.5/п.4) — намеренная поломка стенда
  install-upgrade-uninstall.ps1   стенд, п.3 — install/upgrade/uninstall внутри гостя
  on-off-cycle.ps1                стенд, п.3 — цикл on/off через IPC напрямую
  doctor.ps1                      стенд, п.3 — doctor через IPC напрямую
```

`vmctl.sh` — единственная точка управления: агент не пишет длинные
`virsh`/`ssh` вручную. IP управляющей сети статический (DHCP-резервация по
MAC в `vt-mgmt-network.xml`) — `vmctl.sh ip` его просто возвращает, не
опрашивает `virsh domifaddr` на тестируемой сети (ту как раз ломают тесты).
`vmctl.sh test-ip` — IP в тестируемой (`default`) сети, только для
диагностики со стороны хоста, SSH туда не ходит.

Выполнение команды через guest agent (работает без сети внутри виртуалки):

```sh
virsh qemu-agent-command vt-win10 '{"execute":"guest-exec","arguments":{
  "path":"powershell.exe",
  "arg":["-NoProfile","-ExecutionPolicy","Bypass","-File","C:\\dev\\rescue.ps1"],
  "capture-output":true}}'
# → {"return":{"pid":N}}
virsh qemu-agent-command vt-win10 '{"execute":"guest-exec-status","arguments":{"pid":N}}'
# вывод приходит в base64
```

### 5.4 Снимки

- `clean` — сразу после установки и настройки. **Никогда не удалять.**
- `stage-N` — перед началом каждого этапа.
- `pre-<тест>` — перед каждым опасным тестом; старые `pre-*` агент удаляет сам, оставляя последние 3.

Агент откатывает снимки сам. Откат к `clean` — только если текущий снимок
этапа тоже испорчен; записать причину в «Статус».

### 5.5 Опасные тесты и спасение

Опасный тест — всё, что меняет маршруты, DNS, брандмауэр/WFP или запускает
туннель внутри виртуалки.

**`rescue.ps1`** (внутри виртуалки, первый артефакт этапа 0) —
идемпотентный, не зависит от программы, снимает всё: службу и `xray.exe`,
маршруты и адрес TUN, DNS интерфейсов, WFP-фильтры по GUID (3.9) и правила
брандмауэра по группе, задачу `vt-rescue`. Пишет в
`C:\dev\logs\rescue-<время>.log`, что именно снял.

**`run-test.ps1`** (внутри виртуалки) — один скрипт на тест: применить →
проверить → записать `RESULT: PASS/FAIL` в лог → откатить в `finally`:

```powershell
param([Parameter(Mandatory)][string]$Name, [Parameter(Mandatory)][string]$Script)
$log = "C:\dev\logs\$Name-$(Get-Date -f yyyyMMdd-HHmmss).log"
Start-Transcript $log
try     { & $Script }                       # печатает RESULT: ...
catch   { "RESULT: ERROR $_" }
finally { & C:\dev\rescue.ps1; Stop-Transcript }
```

Проверки связи — всегда с таймаутом (`curl.exe -s --max-time 10 …`).
Тесты, где сеть **должна** пропасть (kill-switch), устроены так же: убить
Xray → убедиться, что `curl` **не** проходит → записать → откатить.

Стенд, п.2 — результат сценария едет ФАЙЛОМ, не текстом консоли: сценарий
(дот-сорсится в `run-test.ps1`) зовёт `Add-Step` на каждую проверку —
вердикт по числам/структуре (SID, Win32-код, HRESULT, exit code), не по
сравнению локализованных строк системных утилит (тот же урок, что с
метками `sc.exe`). `run-test.ps1` сам считает общий вердикт и пишет JSON
(UTF-8 без BOM) в `C:\dev\logs\<имя>-<время>.json`; `with-rescue.sh`
забирает файл по SFTP (путь — с прямыми слешами, не обратными: современный
`scp` только по SFTP, обратные слеши в Windows-пути молча не находят
файл) и печатает вердикт из него, не из транскрипта. Пример сценария —
`tests/vm/scenarios/acl-config-dir.ps1` (проверяет ACL ревью п.2 через
`Get-Acl`/SID, без единого вызова `icacls.exe`).

Гостевые `.ps1`-скрипты обязаны нести UTF-8 BOM (`vm/rescue.ps1` и
`vm/setup-guest.ps1` — уже; `vm/run-test.ps1` и сценарии в
`tests/vm/scenarios/` — тоже). Без BOM PowerShell 5.1 парсит файл в
системной ANSI-кодировке, а не в UTF-8 — кириллица внутри строкового
литерала с `$(...)`-интерполяцией однажды дала не просто "кракозябры",
а настоящую ошибку разбора скрипта (поймано живым тестом при отладке
этого пункта). Из-за этого функциональные строки (`Step`/`Expected`/
`Actual` в `Add-Step`) в сценариях пишутся по-английски — кириллица
остаётся только в комментариях.

`rescue.ps1` при сбросе DNS и обновлении DHCP-аренды теперь явно
пропускает адаптер `vt-mgmt` (стенд, п.1) — иначе `ipconfig /release`
рвёт саму SSH-сессию, через которую `rescue.ps1` запущен: найдено этим
же живым тестом (`run-test.ps1` обрывался с exit 255 ровно на этом шаге,
отчёт не успевал записаться).

**`with-rescue.sh`** (на хосте) — обёртка, через которую агент запускает
любой опасный тест. Цепочка спасения:

1. снимок `pre-<тест>`;
2. внутри виртуалки ставится задача `vt-rescue` (через 10 минут сама запускает `rescue.ps1`; около полуночи задавать дату `/SD`);
3. `run-test.ps1` запускается через SSH под `timeout`; лог копируется на хост в `logs/vm/`;
4. проверка: SSH отвечает и из виртуалки есть интернет (`curl` без туннеля);
5. если SSH не отвечает → `rescue.ps1` через **guest agent**, ждать до 60 с, проверить снова;
6. если guest agent не отвечает или сеть не вернулась → `virsh snapshot-revert pre-<тест>`, отметить тест как `BROKE_VM`;
7. при успехе — снять задачу `vt-rescue`.

Логи — единственный источник правды о том, что происходило без связи:
результат пишется **до** отката, при неудаче агент начинает с чтения лога, а
не с повторного запуска.

Доступ с хоста при включённом kill-switch (стенд, п.1): раньше SSH шёл по
той же сети `virbr0`, что и сами сетевые тесты, и то, что канал это
переживал, было случайностью устройства WFP-фильтров продукта (только
`ALE_AUTH_CONNECT`, исходящие соединения — трафик по уже принятому
входящему SSH-соединению через них не идёт), а не гарантией: появись у
kill-switch когда-нибудь `ALE_AUTH_RECV_ACCEPT`, канал отвалился бы
посреди прогона. Теперь SSH — на отдельном адаптере `vt-mgmt`
(host-only сеть, вне того, что видит и режет продукт), а `default`
(`virbr0`) остаётся только тестируемой сетью. В продукте (WFP, маршруты,
конфиг Xray) исключений для управляющего канала/подсети НЕТ и не должно
быть — изоляция сделана сетью, а не дыркой в фильтрах; если какой-то тест
не проходит без такого исключения, это находка о продукте, а не повод его
добавить.

Подсеть `vt-mgmt` (10.77.77.0/24) не может не пересекаться по числам с
`/1`-маршрутами включённого туннеля — они вместе с `default`-маршрутом
покрывают ВСЕ IPv4-адреса, так что любая выбранная подсеть попадёт в
одну из половин. Это не проблема: у `vt-mgmt` есть свой прямо подключённый
маршрут (`/24`, on-link), который как более специфичный побеждает `/1` по
longest-prefix-match независимо от числового совпадения диапазонов —
подтверждено живым тестом: с включённым туннелем `route print` показывает
`10.77.77.0/24 On-link` отдельной строкой поверх `/1`-покрытия, и SSH при
этом продолжает ходить через `vt-mgmt`. В режиме `--proxy-lan` SSH может
пропасть — это ожидаемо для тестируемой сети, но не должно происходить для
`vt-mgmt` (спасение через guest agent остаётся страховкой на случай, если
всё-таки произошло).

**Статус (стенд, п.1) — проверено живьём**: второй адаптер `vt-mgmt`
поднят на живой `vt-win10`, `sshd` слушает только на `10.77.77.5`
(на тестовом адаптере порт 22 не отвечает вовсе — таймаут, не отказ),
`vmctl.sh` переведён на него. Сценарий из задания: туннель on (kill-switch
по умолчанию включён) → `Disable-NetAdapter Ethernet` → `off` → снятие
диагностики (`status`) → `Enable-NetAdapter` — параллельный опрос SSH
раз в секунду в течение всего сценария не показал ни одного разрыва
(0 FAIL из 39 проверок). Изменения внесены и в `vm/create-vm.sh`/
`vm/setup-guest.ps1` (идемпотентно, для будущего пересоздания стенда с
нуля), но пересоздание stenda "с нуля" целиком в этой сессии не
прогонялось — только применение поверх уже существующей `vt-win10`.

Стенд, п.4 — `with-rescue.sh` спасал сеть, но не саму машину: таймаут
SSH-команды (сценарий завис) раньше просто падал в проверку связи, и
если сеть на вид была цела, скрипт молча объявлял успех, хотя зависший
на госте процесс не гарантирует, что его `finally`/`rescue.ps1` вообще
выполнился. Теперь таймаут (`timeout` вернул 124) сразу ведёт к
`virsh snapshot-revert` на снимок `pre-<тест>`, без попытки "подлатать"
через guest agent — довериться частичному восстановлению здесь неверно.

Этим же живым тестом поймана отдельная, более старая находка: очистка
старых `pre-*` снимков ("оставить последние 3") сортировала снимки по
ИМЕНИ, а не по времени — снимки разных тестов вперемешку
(`pre-acl-config-dir-...`, `pre-break-svc-...`, `pre-hang-test-...`)
сортируются по алфавиту не в хронологическом порядке, и однажды это
удалило только что созданный снимок ДО того, как он понадобился;
`snapshot-revert` тогда падал с "снимок не найден", а скрипт этого не
замечал и всё равно докладывал об успехе. Сортировка исправлена на
колонку "Время создания" самого `virsh`.

**Статус (стенд, п.4) — проверено живьём**: сценарий из задания
(`tests/vm/scenarios/break-service-killswitch.ps1` — туннель on,
kill-switch поднят, служба убита `Stop-Process -Force`) сеть не портит
настолько, чтобы её не восстановил уже существующий шаг 5 (guest agent
`rescue.ps1`) — до отката дело не дошло, стенд остался цел без ручного
вмешательства. Отдельно, короткой копией таймаута (20 с вместо 1200)
и зависающим сценарием (создаёт файл-маркер, затем спит дольше
таймаута) подтверждено само новое поведение: таймаут детектируется,
`with-rescue.sh` откатывает снимок МИНУЯ проверку сети, и после отката
файл-маркер, созданный ПОСЛЕ снимка, действительно пропадает — то есть
откат — настоящий, не просто строка в логе. Реальный прогон с полным
1200-секундным таймаутом (20 минут) не делался — непрактично по времени
в рамках сессии, но сама логика детектирования и отката от значения
таймаута не зависит.

### 5.6 Сборка и доставка на стенд

- юнит-тесты (Core/Native) по-прежнему гоняются на хосте (`dotnet test`, кросс-платформенно, без Windows) — это самый быстрый цикл при правке кода, стенд для них не нужен;
- **стенд, п.3**: прогон СЦЕНАРИЯ (build+install+тест) целиком внутри гостя, не на хосте. `with-rescue.sh` синхронизирует исходники в `C:\dev\src` (`git archive` -> `tar` по SSH, без `.git`/`bin`/`obj`, доли секунды), сам сценарий (дот-сорсится в `run-test.ps1`, как и в п.2) при необходимости зовёт `vm/guest-build.ps1` — тот собирает все три проекта (`dotnet publish ... --self-contained true`, тот же режим, что CI), кладёт `xray.exe`/`wintun.dll` (кэш в `C:\dev\build-cache`, sha256 по `vm/pinned-versions.txt`, качается заново только если пин изменился) и компилирует установщик через ISCC (без подписи — подпись только в CI, см. `.github/workflows/build.yml`). Хосту после этого нечего гонять туда-сюда, кроме исходников и итогового JSON-отчёта (п.2);
- `.NET SDK` и Inno Setup теперь тоже часть стенда (`vm/setup-guest.ps1`), не только хоста — на голом `vt-win10` их ставит `dotnet-install.ps1`/`innosetup-*.exe` тихой установкой;
- сценарии, которые говорят с самой службой (on/off/doctor/status), делают это НАПРЯМУЮ по именованному каналу — `Invoke-VtIpc` (в `run-test.ps1`, доступна всем сценариям) шлёт `{"Cmd":...}` и разбирает структурный JSON-ответ, а не текст, который печатает `VlessTunnel.Cli.exe` для человека (тот же принцип п.2: вердикт по структуре, не по тексту);
- тестовая ссылка (отдельный UUID на сервере, не основной) лежит на хосте в `~/.config/vless-tunnel-dev/test-link.txt` — пока НЕ автоматически копируется в `C:\dev\secrets\` (см. «Статус» ниже, известный пробел); сценарии сейчас полагаются на персистентный `C:\ProgramData\vless-tunnel\link.txt`, переживающий переустановку.

**Статус (стенд, п.3) — проверено живьём**: три сценария из задания
(`tests/vm/scenarios/install-upgrade-uninstall.ps1`,
`on-off-cycle.ps1`, `doctor.ps1`) прогнаны через `with-rescue.sh` на
живом `vt-win10` — все три дали честный `PASS` со структурными
проверками (`Get-Service`/`Get-NetAdapter`/`Get-NetRoute`/IPC-ответ, ни
разу текст `Setup.exe`/`unins000.exe`/`VlessTunnel.Cli.exe`). Сборка
внутри гостя подтверждена: `dotnet publish` трёх проектов + ISCC
произвели реальный `vless-tunnel-setup.exe`, установка/переустановка
поверх (тот же код-путь, что настоящий апгрейд, `ServiceExists=True` в
`.iss`)/удаление прошли по-настоящему (не подмена файлов вручную).
Найдена и обойдена помеха окружения (не продукта): трей, оставшийся
от предыдущего интерактивного сеанса, держал открытым общий рантайм-DLL

перезапускать процессы из чужой сессии, поэтому сценарий закрывает
трей заранее.

**Осталось открытым**: доставка `test-link.txt` с хоста в
`C:\dev\secrets\` для сценариев на СВЕЖЕМ стенде (без персистентного
`link.txt` от прошлых сессий) — не сделано в этой сессии, сценарии
падают понятным `FAIL`, если ни того, ни другого нет, а не молча. Сама

    возвращаются к состоянию до `on` (0 лишних записей).
  - **Найден и исправлен второй баг живым тестом**: `RouteWatcher`
    реагировал на СВОИ ЖЕ изменения таблицы маршрутов (добавление
    `/1`-маршрутов само порождает NotifyRouteChange2), из-за чего
    `RecomputeHostRoute` уходил в бесконечный цикл и в итоге перекидывал
    хост-маршрут до сервера через сам TUN — ту самую петлю, от которой
    он должен защищать. Исправлено окном подавления (2 с) после любой
    собственной мутации маршрутов/адресов.
  - **Третий баг найден и исправлен**: причина нестабильного времени
    появления TUN-адаптера (от ~1 с до таймаута в 40 с) — `Process.Start`
    с `RedirectStandardOutput/Error=true` без вычитывания потоков.
    Анонимные pipe'ы ОС имеют ограниченный буфер; когда он заполнялся
    логами xray.exe, процесс блокировался на записи в свой же stdout —
    а значит блокировалась и вся дальнейшая инициализация, включая
    поднятие TUN. Исправлено: `BeginOutputReadLine`/`BeginErrorReadLine`
    с обработчиками, пишущими строки xray в общий лог службы через
    `_log` (с префиксом `xray:`/`xray[err]:`) — pipe теперь вычитывается
    постоянно, асинхронно. Побочная находка при разборе логов xray:
    Windows шлёт много NetBIOS-широковещательных UDP:137-запросов через
    TUN сразу после его поднятия — ожидаемо (роутится в `direct` по
    правилу приватных сетей), но объясняет неожиданно большой объём
    логов при полном выводе xray.
  - **Подтверждено 5 подряд чистыми циклами on→off** (по 10 с) после
    фикса: адаптер поднимается за ~0–1 с КАЖДЫЙ раз, ни одного
    таймаута; после каждого `off` — 0 процессов xray.exe, 0 адаптеров
    xray0, таблица маршрутов чистая.
  - **Четвёртый баг найден и исправлен**: даже с окном подавления (2 с)
    после собственных мутаций, `RecomputeHostRoute` один раз словил
    отложенное событие (вероятно, Windows NLA профилирует новую сеть уже
    после появления TUN-адаптера) и снова получил от `GetBestRoute2`
    сам TUN как "лучший маршрут" к серверу — окно подавления по времени
    не универсально. Добавлен жёсткий инвариант, не зависящий от
    таймингов: если пересчитанный интерфейс == TUN-интерфейс, результат
    отбрасывается, восстанавливается предыдущий известный хороший шлюз.
  - **Живучесть при смене физического адаптера — подтверждена**
    (`Disable-NetAdapter`/`Enable-NetAdapter` посреди сеанса, на
    полностью чистом снимке `clean`, чтобы исключить накопленные
    артефакты вечера): при разрыве `RecomputeHostRoute` один раз увидел
    "маршрут через сам TUN", отверг его по инварианту выше и восстановил
    прежний шлюз; сама попытка восстановления один раз не удалась, пока
    физический адаптер был ещё выключен (`CreateIpForwardEntry2 failed`)
    — самоисцелилось на следующем срабатывании ~3 с спустя. Туннель
    доработал полный `--duration`, после `off` — 0 процессов, 0
    адаптеров, чистая таблица маршрутов.
  - **Известное ограничение (не решено)**: в узком окне между неудачной
    попыткой восстановить хост-маршрут и следующим срабатыванием
    `RecomputeHostRoute` (в тесте — около 3 с) анти-петлевого
    хост-маршрута до сервера нет вовсе, то есть трафик к серверу в этот
    момент теоретически может пойти через `/1`-маршруты в сам TUN.
    Для этапа 2 (нет kill-switch) это не проверялось отдельно; для
    этапа 3 (kill-switch должен по умолчанию резать трафик мимо TUN)

    рвёт туннель надолго, после `off` таблица маршрутов как до `on`.

    1. (юнит-тестом, до стенда) `FWP_DATA_TYPE` по памяti брался как
       `FWP_UINT8=0`, а на самом деле enum начинается с `FWP_EMPTY=0`,
       `FWP_UINT8=1` — тихо неверные условия фильтра без единой ошибки.
    2. (юнит-тестом) union `{UINT64 rawContext; GUID providerContextKey}`
       внутри `FWPM_FILTER0` по ошибке был смоделирован двумя подряд
       идущими полями вместо `FieldOffset`-объединения — сдвигало все
       смещения после него на 8 байт.
    3. (живым тестом) `FwpmProviderAdd0` падал с `FWP_E_NULL_DISPLAY_NAME`
       — `displayData.name` обязателен, был не проставлен.
    4. (живым тестом, самый серьёзный) **настоящий краш процесса**
       (`STATUS_ACCESS_VIOLATION` в KERNELBASE.dll, подтверждено дампом
       Windows Error Reporting) — `FWP_CONDITION_VALUE0.uint64` это
       `UINT64 *` (указатель на значение, "cannot be null" по
       документации), а не встроенное 8-байтное значение, как
       `uint8`/`uint16`/`uint32` в том же union'е. LUID TUN-интерфейса
       клался в поле напрямую, WFP пытался разыменовать его как адрес
       памяти. Исправлено выделением реальной памяти под значение.
       Место падения найдено пошаговым логом каждого вызова
       `FwpmFilterAdd0` (упал именно на условии по LUID) — без этого
       падение процесса без диагностики было неотличимо от зависания.

    проходит; `Stop-Process xray -Force` → интернет **пропадает**
    (проверено TCP-соединением к 1.1.1.1:443, до этого — работало);

    то есть уже снято самим `KillSwitch.Uninstall()`), таблица
    маршрутов чистая.

    подтверждены живым тестом.** `KillSwitch.Install` получил `excludeLan`

## Этап 6: установщик — впервые живьём на стенде

`installer/vless-tunnel.iss` (без строк подписи — сертификата ещё нет)
скомпилирован реальным `ISCC.exe` (Inno Setup 6.7.3, установлен на
стенд вручную, скачан с GitHub-релиза jrsoftware/issrc — сайт
jrsoftware.org отдаёт HTML-страницу загрузок, а не сам файл, по
"стабильной" ссылке) и прогнан через полный цикл на стенде: чистая
установка → обновление поверх → удаление с ответом «Нет» → переустановка
(проверка, что настройки подхватились) → удаление с ответом «Да» →
установка → тихое удаление (`/VERYSILENT`). Все шаги — вживую, кликами
через QMP (UAC-подтверждение и оба варианта диалога "Удалить
настройки?" тоже реальными кликами, не `/VERYSILENT`).

- **Найдены и исправлены два реальных бага, оба обнаружены только живым
  прогоном — юнит-тестов на .iss-скрипты не бывает:**
  1. **Служба никогда не регистрировалась.** `BinPath` в `[Code]` уже
     оборачивался в кавычки сам (`'"' + exe + '" service'`), а затем ЕЩЁ
     РАЗ оборачивался при подстановке в команду `sc create` — двойные
     внешние кавычки ломали синтаксис, `sc.exe` получал испорченную
     строку. Хуже того, `Exec(...)` не проверял `ResultCode`, поэтому
     установщик рапортовал об успехе, а служба просто не появлялась —
     это не поймать иначе как проверкой `sc query` после живой
     установки. Исправлено на правильный Windows-формат
     (`binPath= "\"C:\...\App.exe\" service"` — внешние кавычки на весь
     аргумент, внутренние \"…\" на сам путь к exe, как в документации
     Microsoft) и добавлена проверка `ResultCode` с жёстким падением
     установки при ошибке `sc create`, чтобы такая поломка больше не
     проходила молча.
  2. **Ссылка на сервер не переживала ДАЖЕ обычный перезапуск службы**,
     не говоря уже об обновлении поставщиком — `TunnelController`
     держал распарсенную ссылку только в памяти процесса, нигде не
     сохранял. Это не баг конкретно установщика, а отсутствующая
     фича, которую критерий приёмки этапа 6 ("обновление поверх —
     настройки на месте") сделал видимой первым же тестом. У
     Linux-версии есть `ETC_DIR/config.json` для этого же — у Windows
     не было ничего. Добавлено: `TunnelController` теперь пишет сырой
     текст ссылки в `link.txt` рядом с `config-service.json` (то есть
     в `%ProgramData%\vless-tunnel`) при каждом успешном `set-link` и
     пытается загрузить его при старте — если файла нет или он не
     парсится, тихо остаётся в состоянии "ссылка не задана", ошибка
     только в лог.
- **Подтверждено живьём, все критерии приёмки этапа 6 (кроме подписи):**
  чистая установка регистрирует и сразу запускает службу
  (`sc query` → RUNNING), обновление поверх останавливает-заменяет-
  перезапускает без потери настроек, автозапуск-ярлыки (Пуск и

  вопроса — тоже по плану ("тихое удаление настройку сохраняет").
- **Не проверено и не могло быть проверено в этом проходе** (нет

## Этап 3.9/7: `sc failure` и проверка часов в `doctor`

Два пропуска из раздела 3.9 плана, замеченных при повторном чтении уже
после того, как основной цикл установщика был подтверждён живьём.

- **`sc failure`.** Служба регистрировалась установщиком без действий
  при сбое — падение процесса (необработанное исключение и т.п.)
  оставляло туннель выключенным до ручного вмешательства, а с
  включённым kill-switch — без интернета вовсе, до перезапуска
  вручную. Добавлен вызов `sc failure ... reset= 86400 actions=
  restart/5000/restart/30000/restart/60000` в `InstallOrUpdateService`
  (и на create, и на update — идемпотентно). **Проверено живьём**:
  `sc qfailure vless-tunnel` после установки подтверждает все три
  действия и период сброса счётчика.
- **Проверка часов в `doctor`.** REALITY и TLS ломаются при сбитых
  часах (частое дело в виртуалках) — `doctor` не предупреждал об
  этом вовсе. Добавлен `VlessTunnel.Core.ClockCheck` — сверяет
  локальное UTC-время с заголовком `Date` от `https://
  www.cloudflare.com/` (не отдельный NTP-клиент — незачем ещё один
  протокол/порт ради одной проверки, когда HTTPS:443 и так нужен
  остальному приложению), с грубой компенсацией сетевой задержки
  (половина RTT). Порог предупреждения — 5 минут (REALITY/TLS обычно
  переживают секунды-десятки секунд расхождения, ломаются на
  минутах). Подключено в обоих местах, где есть `doctor`: standalone
  (`VlessTunnel.Service.exe doctor`, без службы) и IPC-команда
  (`IpcResponse.DoctorClockSkewSeconds`/`DoctorClockError`, печатает
  CLI). 4 юнит-теста на подставном `HttpMessageHandler` (без реальной
  сети — детерминированно и быстро, как остальные тесты репозитория).
  **Проверено живьём обоими путями** (CLI через IPC и standalone) — в
  норме печатает "в порядке", после `Set-Date` вперёд на 3 часа
  корректно предупреждает о расхождении ~10800 с; часы возвращены
  на стенде обратно сразу после проверки.

## Этап 7: captive portal — «Пустить на 5 минут напрямую»

Первая версия (снять только WFP-фильтры kill-switch'а, оставив
маршруты и TUN как есть) была архитектурно неполной — поймано ДО
живого теста, при повторном чтении собственного кода: пока подняты
`/1`-маршруты через TUN, весь трафик всё равно роутится в адаптер, а
не напрямую через физический — xray без рабочего апстрима (именно
ситуация captive portal) молча дропает такие пакеты. Сняв только
фильтры, пользователь остался бы ровно в том же тупике, просто без
явной блокировки на уровне WFP.

Переделано на честный путь: `TunnelController.CaptivePortalBypassAsync`
делает полный `off` (маршруты+TUN+kill-switch снимаются вместе тем же
проверенным кодом, что и обычное выключение), запоминает, что туннель
был включён, и через заданное время (5 минут) сама вызывает `on`
заново. Никакого нового частичного пути в `TunnelManager` не
понадобилось — весь эффект получен переиспользованием уже
живо-проверенных `StartAsync`/`StopAsync`.

Команда `captive-portal`: IPC + CLI + два пункта в трее (в меню
главного окна и отдельным пунктом прямо в контекстном меню трея, не
только через открытие окна — по духу самой функции: пользователь
застрял без интернета и хочет сделать что-то быстро, а не идти в
меню окна).

- **Проверено живьём на стенде** (таймер временно сокращён до 15 с
  только для теста, не для коммита): подняли реальный туннель (`on`,
  прямая связность подтверждена) → `captive-portal` → статус
  немедленно `Off`, `Get-NetAdapter` подтверждает исчезновение
  `xray0`, прямой интернет работает (`TcpTestSucceeded: True`) → после
  истечения таймера статус САМ вернулся в `On`, адаптер `xray0` снова
  поднят → `test` подтвердил рабочий прокси (HTTP/SOCKS5/TCP OK).
  Полный цикл, без единого ручного вмешательства между `captive-portal`
  и автоматическим восстановлением.

## Этап 7 (доведён): `update-core` и `self-update`

`GitHubReleaseClient` (Core, тестируется подставным `HttpMessageHandler`,
без реальной сети) — общая часть: узнать последний релиз через
`api.github.com`, скачать файл, посчитать sha256, разобрать `.dgst`
(формат "SHA2-256= &lt;hex&gt;", тот же, что уже разбирает Linux-версия).

- **`update-core`** (`TunnelController.UpdateCoreAsync`): последний
  релиз XTLS/Xray-core → `Xray-windows-64.zip` → сверка sha256 с
  `.dgst` → замена `xray.exe`/`wintun.dll` с резервной копией. Если
  туннель был включён — перепроверяет `TunnelTester` после замены;

  обратно на старом ядре (пользователь не остаётся без интернета из-за
  неудачного обновления).
- **`self-update`** (`SelfUpdater`, план 3.9: "сверка sha256 **и**
  отпечатка подписи с зашитым"): последний релиз
  RamDll/vless-tunnel-windows → `vless-tunnel-setup.exe` +
  `.sha256` → сверка суммы → извлечение Authenticode-сертификата из
  скачанного exe и сверка отпечатка с зашитым в
  `SelfUpdater.ExpectedCertThumbprint` (тот же, что в
  `installer/trust.ps1`) → только при совпадении ОБОИХ — тихий запуск
  (`/VERYSILENT`, настройки сохраняются — путь уже проверен в этапе 6).
- **Найден и исправлен архитектурный баг живым тестом**: скачивание
  запускалось ДО выключения туннеля — но пока kill-switch активен,

  `update-core` — при выключенном туннеле (файл реально перезагружен:

  `self-update` — на реальном релизе `v0.0.2`: sha256 и отпечаток

## Три бага с реальной машины тестировщика — найдены и исправлены

Тестировщик поставил программу на свою машину (не стенд) и прислал
скриншот: трей показывает "Туннель включён", а браузер тут же рядом —
`DNS_PROBE_STARTED`. Следом ещё сообщения: новую ссылку вставить не
даёт, после принудительного закрытия и повторного запуска — пустое
белое окно, а через PowerShell (то есть с повышением) всё почему-то
работает. Три разных на вид симптома оказались тремя независимыми
багами.

1. **DNS не резолвился через TUN.** Код никогда не назначал DNS-сервер
   самому адаптеру `xray0` — только внутри `dns`-секции конфига Xray,
   которая резолвит для самого Xray, но не помогает Windows понять,
   кого спросить для доменов, ушедших в TUN по `/1`-маршрутам. Сырой
   TCP по IP через туннель работал (что и объясняет, почему это не
   всплыло раньше ни на одном из стендовых прогонов `test` — тогда
   ловилась то FAIL, то OK, списывалось на нестабильность сети стенда,
   см. запись про `update-core` выше — на самом деле FAIL был системным,
   просто с эффектом присутствия из-за случайных попаданий в кэш/иные
   пути резолва). Исправлено: `WindowsConfigOptions.DnsServers`
   (`1.1.1.1`, `8.8.8.8` по умолчанию) + `TunnelManager.SetTunDns` —
   `netsh interface ip set/add dns` на сам адаптер сразу после
   назначения ему IP-адреса. Явного снятия не требуется — настройка
   гибнет вместе с адаптером при остановке `xray.exe`.
2. **Установщик никогда не передавал службе, кого пускать по
   IPC-каналу.** ACL именованного канала службы (`IpcServer`) разрешает
   без `--allow-user` только SYSTEM и группу "Администраторы" **при
   полном повышении прав** — а обычный запуск трея (без "Запуск от
   имени администратора") у Windows идёт с урезанным токеном даже для
   учётки из группы администраторов (UAC split-token, подтверждено
   отдельным P/Invoke-скриптом через `OpenProcessToken`+
   `WindowsIdentity` на живом процессе). Отсюда и "не даёт вставить
   ссылку" (запрос по каналу отклонялся), и "через PS работает"
   (PowerShell тестировщик запускал от администратора, с полным
   токеном). Не всплыло раньше, потому что весь этот сеанс на стенде
   трей запускался только через Планировщик заданий с повышением —
   маскировало баг целиком. Исправлено: `binPath` в `sc create`/`sc
   config` теперь включает `--allow-user "<{username}>"` (тот, кто
   ставит программу — тот же, кто подтверждал UAC), `Program.cs`
   разбирает `--allow-user` в режиме `service`.
3. **Пустое белое окно при любом сбое IPC.** `MainWindow` показывала
   один из двух панелей (`_onboardingPanel`/`_configuredPanel`) только
   внутри `ApplyStatus`, которая вызывалась исключительно при УСПЕШНОМ
   ответе от службы — при отказе или исключении обе панели оставались
   `Visible=false`, и пользователь видел голое пустое окно без единой
   подсказки, что случилось. Исправлено: новая `_connectionErrorPanel`
   ("Не удаётся подключиться к службе" + причина + кнопка "Повторить")
   показывается в обеих ветках `RefreshStatusAsync` при неуспехе;
   `ShowSetLinkDialogAsync` теперь также показывает `MessageBox` с
   текстом ошибки (раньше уходило только в скрытый журнал).

**Проверено живьём на стенде**, все три вместе, в связке: свежий
`VlessTunnel.Tray.exe`, запущенный не из Планировщика с повышением, а
обычным двойным щелчком по иконке в трее (без прав администратора) —
окно открылось сразу с онбордингом (не пустое); вставка новой ссылки
через диалог "Настроить" прошла с первого раза и без зависаний,
экран мгновенно переключился на настроенный вид; после перезапуска
стенда (`virsh reset` — `virsh reboot` не подействовал, гостевая ОС не
отреагировала на ACPI-сигнал) служба, поднятая с `start= demand` (флаг
автозапуска при установке не был выбран), поднялась вручную (`sc
start`) — трей корректно подхватил уже сохранённый конфиг сервера;
включение туннеля прошло чисто; `test` показал `DNS: OK` (раньше
стабильно `FAIL`); `netsh interface ip show dns name=xray0` подтвердил
оба назначенных сервера; и главное — в реальном Microsoft Edge
(не через CLI) страница `https://example.com/` открылась штатно, без
`DNS_PROBE_STARTED`, то есть именно то, что было сломано на скриншоте
тестировщика.

Попутно найдена методологическая ловушка при автоматизации теста через
UI Automation: `InvokePattern.Invoke()` на WinForms-кнопке, открывающей
модальный диалог (`ShowDialog`), не возвращает управление вызывающему
процессу, пока диалог не закроется — если в этот момент прибить
вызывающий процесс, автоматизационное дерево целевого приложения может
зависнуть насовсем (перезапуск трея решил). Рабочая связка для
скриптовой проверки: клик по кнопкам — через QEMU `input-send-event`
(реальные аппаратные события мыши), а вставка текста в поле — через
`ValuePattern.SetValue` (не зависит от фокуса ОС и не блокируется).
`SendKeys` для этого не подходит вовсе: любой новый процесс,
запущенный для отправки клавиш (даже `-WindowStyle Hidden`), может
на мгновение перехватить фокус переднего плана при создании, и ввод
уходит не в целевое окно, а в него самого.

## Настоящая (не самоподписанная) подпись установщика — заявка в SignPath

Владелец спросил про нормальный сертификат кодовой подписи вместо
самоподписанного + `trust.ps1`. Платные варианты (обычный OV-сертификат
у CA типа DigiCert/Sectigo, Microsoft Trusted Signing) стоят от
~$10/мес до ~$500/год и требуют верификации личности — решение и оплата
остаются за владельцем. Из полностью бесплатных вариантов актуален на
2026 год один: **SignPath Foundation** (signpath.org) — бесплатная
подпись для open source через их CI-пайплайн; Certum, который раньше
тоже был бесплатным для OSS, теперь платный (~49€/год).

Условия SignPath: репозиторий должен быть под OSI-одобренной лицензией
(у репозитория её не было — добавлен `LICENSE`, MIT), заявка подаётся
через форму на signpath.org, дальше ручная проверка проекта. Каждый
релиз требует подтверждения подписи на их стороне (не полностью
автоматический CI) — это их модель, не наша недоработка.

**Сделано агентом (не требует владельца):**
- `LICENSE` (MIT) — обязательное условие для заявки.
- `.github/workflows/build.yml` — три новых шага (`Upload unsigned
  installer for SignPath` → `Submit signing request to SignPath` →
  `Replace installer with the SignPath-signed version`), встроены
  между компиляцией и подсчётом sha256, гарантированно проверены на
  безобидность (`SIGNPATH_API_TOKEN` в репозитории не заведён — все три
  шага пропускаются, сборка идёт по-старому через самоподписанный
  `.pfx`, живой прогон CI после этого коммита прошёл зелёным). Ветка
  самоподписанной подписи в "Compile installer" теперь условно
  выключается, если задан `SIGNPATH_API_TOKEN` — не подписывать дважды.

**Нужно от владельца (агент сделать не может — сторонний сервис,
верификация личности):**
1. Подать заявку на signpath.org (раздел Open Source) — email, ссылка
   на репозиторий, короткое описание проекта и почему нужна подпись.
2. После одобрения — создать проект в портале SignPath, оттуда взять
   `organization-id`, `project-slug`, названия signing-policy (обычно
   `release-signing`/`test-signing`).
3. Завести в GitHub (Settings репозитория):
   - Secret `SIGNPATH_API_TOKEN` — токен роли Submitter из портала.
   - Variables `SIGNPATH_ORGANIZATION_ID`, `SIGNPATH_PROJECT_SLUG`.
   - Если реальные имена signing-policy в портале отличаются от
     `release-signing`/`test-signing` — поправить строку в `build.yml`
     (`signing-policy-slug:`).
4. Установить приложение "SignPath" из GitHub Marketplace на этот
   репозиторий (Settings → GitHub Apps) — без него экшен не подтвердит
   источник сборки, это отдельный шаг помимо секретов.

После этого при следующем пуше тега `v*` установщик подпишется
настоящим сертификатом автоматически, `trust.ps1`/самоподписанный путь
перестанет требоваться новым пользователям (старый self-signed путь
остаётся в коде как fallback, ничего не удалено).

## Ещё три бага, найденные по свежим сообщениям тестировщиков

После релиза v0.1.0 пошли новые сообщения: у одного тестировщика (свою
VM создал и тестирует сам) — нестабильность, медленный интернет и
"зависание" при переключении из трея; у параллельного тестировщика —
скриншот "Не удаётся подключиться к службе / The operation has timed
out" сразу после перезагрузки. Разобрано по фактам, не по догадкам:

1. **Служба ставилась с `DEMAND_START` (не автозапуск), несмотря на
   чекбокс "включён по умолчанию" в мастере.** Причина —
   задокументированное (но неочевидное) поведение Inno Setup: `/VERYSILENT`/
   `/SILENT` не выбирают вообще никаких задач по умолчанию, включая
   `checkedonce`, если не передать `/TASKS=` явно. `self-update` всегда
   вызывает установщик именно так — то есть КАЖДЫЙ self-update отправлял
   бы дальше работающих пользователей на неавтозапускающуюся службу.
   Подтверждено живым экспериментом на стенде: свежая `/VERYSILENT`-
   установка v0.1.0 давала `DEMAND_START` вживую, не в теории. Именно
   это объясняет скриншот параллельного тестировщика — после
   перезагрузки служба просто не поднялась, трей закономерно не смог
   достучаться по каналу за 10 секунд таймаута.
   **Исправлено**: убрал зависимость вообще — `[Tasks]` `autostartservice`/
   `autostarttray` полностью удалены из `.iss`, служба всегда ставится
   `start= auto`, ярлык автозапуска трея создаётся всегда без `Tasks:`.
   Раз до `set-link`+"Включить" служба ничего не делает и никуда не
   стучится, автозапуск по умолчанию безопасен и предсказуем.
   **Проверено живьём**: чистая переустановка (`sc create`, не
   `sc config` — апгрейд-ветка не проверяет код возврата и могла бы
   скрыто проглотить ту же ошибку, отдельный риск на будущее) → `sc qc`
   → `AUTO_START`; ярлык в Startup — есть.
2. **`self-update` под `/VERYSILENT` молча откатывал ВСЮ установку,
   если трей запущен.** Найдено тем же экспериментом: RestartManager
   пытается закрыть `VlessTunnel.Tray.exe` (обычное дежурное состояние
   трея), не успевает/не может, тихий режим на диалог Abort/Retry/Ignore
   отвечает Abort по умолчанию — установщик "успешно" завершается,
   ничего не поменяв, а `SelfUpdater` об этом даже не узнаёт (не ждёт
   и не проверяет результат процесса установщика). **Исправлено**:
   `SelfUpdater.CloseRunningTray` теперь сам закрывает все процессы
   `VlessTunnel.Tray` (сначала штатно `CloseMainWindow`, затем `Kill`
   через 3 с) непосредственно перед запуском установщика — не полагаемся
   на RestartManager внутри тихого инсталлятора.
3. **У `VlessTunnel.Tray` нет защиты от повторного запуска.** Не
   подтверждено на 100% как причина конкретного "зависания" (само
   переключение туннеля из трея на чистом стенде с одним процессом
   отработало штатно — включилось за ~10 с, без ошибок, держалось
   стабильно), но это реальная, не гипотетическая дыра: автозапуск при
   входе + случайный повторный запуск (ярлык, двойной клик) — и получаются
   два независимых значка с двумя независимыми IPC-подключениями,
   что объясняет и путаницу, и непредсказуемое поведение по нажатию
   "Включить/выключить". Тот же класс проблемы уже ловился в этой
   сессии — только с ДВУМЯ ЗАПУЩЕННЫМИ СЛУЖБАМИ вместо трея (см. запись
   про этап 4 живого теста set-link). **Исправлено**: именованный Mutex
   в `Program.cs` — второй запуск сразу показывает "vless-tunnel уже
   запущен" и завершается, не создавая второй значок.

**Не подтверждено и остаётся открытым**: изначальная жалоба на общую
"нестабильность и медленный интернет". TUN-стек (`gvisor`, userspace-
эмуляция TCP/IP) зашит жёстко, альтернатива `system` (нативный стек
Windows) в коде есть, но не вынесена ни в CLI-флаг, ни куда-либо ещё —
кандидат на проверку, если после фиксов выше жалобы на скорость
останутся.

### 1. Установщик ломает IPC после self-update — подтверждено, исправлено

Диагноз ревью подтверждён живым тестом ДО фикса: установщик, запущенный
из SYSTEM-контекста (та же схема вызова, что `SelfUpdater.Process.Start`
из процесса самой службы), даёт `--allow-user` с именем системной
учётки вместо реального пользователя — `sc qc` показал
`--allow-user "Система"` после симулированного self-update
неисправленной сборкой.

**Исправлено** (`installer/vless-tunnel.iss`): при апгрейде поверх уже
существующей службы (`ServiceExists=True`) имя пользователя больше не
берётся из `{username}` (ненадёжно — зависит от того, КТО/ЧТО запустило
Setup.exe), а читается из уже зарегистрированного `ImagePath` службы в
реестре (`GetExistingAllowUser`/`ExtractAllowUser`) — не через `sc qc`,
у его текстового вывода локализованные подписи полей (на русской
Windows `BINARY_PATH_NAME` превращается в нечитаемый текст, парсить по
метке ненадёжно). `{username}` используется только при ПЕРВОЙ установке,
когда службы ещё нет — единственный момент, когда он гарантированно
совпадает с интерактивным пользователем, подтверждавшим UAC. Заодно
ветка `sc config` теперь тоже проверяет код возврата и кидает
`RaiseException` при сбое (раньше — только `sc create`).

**Проверено живьём** через `with-rescue.sh` (лог:
`logs/vm/allowuser-20260918-230722.host.log`): чистая переустановка →
`sc qc` → `--allow-user "vtadmin"`; `set-link`+`status` от имени
`vtadmin` БЕЗ повышения (через Планировщик заданий `/RU vtadmin`, без
`/RL HIGHEST`) — отвечает корректным JSON; симулированный self-update
(установщик от SYSTEM) → `sc qc` → `--allow-user "vtadmin"` (было бы
`SYSTEM` без фикса) → тот же неэлевированный `vtadmin` снова получает
корректный `status` без отказа в доступе. `RESULT: PASS`.

Отступление от буквального сценария владельца: "чистая установка
обычным мастером" заменена на `/VERYSILENT` для воспроизводимости теста
(тот же код `InstallOrUpdateService`, что и у мастера, разницы в
исследуемой логике нет — GUI-путь при обычном/не-self-update апгрейде
не менялся и не является источником этого бага).

### 2. Права на каталог конфига — подтверждено, исправлено

Диагноз подтверждён `icacls` до фикса: `BUILTIN\Пользователи:(I)(OI)(CI)(RX)`
на `%ProgramData%\vless-tunnel` — наследуемое право, группе "Users"
(то есть любому локальному пользователю) разрешено чтение. `link.txt`
(секретный UUID/pbk/sid) и `config-service.json` лежали открытым
текстом для кого угодно — редакция UUID в логах (`Redact.cs`) действительно
не имела смысла на этом фоне.

**Исправлено** (`VlessTunnelWindowsService.OnStart` →
`SecureConfigDirectory`): при каждом старте службы (не только при первом
создании каталога — чтобы каталоги от установок ДО фикса тоже
приводились к нужным правам) на `_workDir` ставится `DirectorySecurity`
с `SetAccessRuleProtection(true, false)` (снять наследование, не
сохранять унаследованные правила) и только двумя ACE: SYSTEM +
Администраторы, `FullControl`, с наследованием на файлы/подкаталоги —
план (раздел 2) требует ровно это.

**Проверено живьём** через `with-rescue.sh` (лог:
`logs/vm/acl3-20260918-231847.host.log`, плюс отдельная диагностика
`Get-Content diag-out4.txt`/ручная проверка — см. ниже про ложный FAIL):
`icacls` после фикса — только `NT AUTHORITY\Система:(OI)(CI)(F)` и
`BUILTIN\Администраторы:(OI)(CI)(F)`, группы "Пользователи" нет вовсе.
Второй, заведомо непривилегированный локальный пользователь (`vtuser2`,
НЕ в группе Администраторы) не может прочитать ни `link.txt`, ни
`config-service.json` ("Отказано в доступе" в обоих случаях) — и это
закрывает так же зависший с этапа 4 критерий приёмки "чужой пользователь
не может управлять туннелем": попытка `status` от его имени по
именованному каналу вернула `Access to the path is denied` для
`\\.\pipe\vless-tunnel` (ACL канала сам, независимо от прав на файлы,
уже правильно отсекает не-`--allow-user` пользователя). `vtadmin`
(легитимный `--allow-user`) продолжает работать как раньше.

Технический нюанс теста: автоматическая PASS/FAIL-проверка в самом
тестовом скрипте пометила шаги 4 как `FAIL` — но это ложное
срабатывание её собственной регулярки, не проблема фикса: текст
"Отказано в доступе"/"Access is denied" прошёл через несколько
перекодировок (гостевая консоль → SSH → локальный grep) и не совпал по
буквам, при этом содержательно (короткое сообщение об ошибке, 21 байт,
без единого совпадения `vless://` в выводе — то есть секрет точно не
утёк) однозначно подтверждает отказ в доступе. Обошёл вручную сверкой
байтов, а не полагался на регулярку. Также по пути обнаружено и решено:
`schtasks /RU` для стороннего (не `vtadmin`) пользователя тихо создаёт
задачу, которая никогда не запускается, если у пользователя нет права
"Log on as a batch job" (`SeBatchLogonRight`) — обычные локальные
пользователи получают его не по умолчанию, в отличие от `vtadmin`
(который весь этот сеанс негласно имел его из более ранних тестов).
Выдано через `secedit` на время теста — не относится к продукту, чисто
особенность тестовой методологии для ВТОРОГО пользователя.

### 3. self-update проверял отпечаток, но не саму подпись — подтверждено, исправлено

Диагноз верен: `X509Certificate.CreateFromSignedFile` только извлекает
сертификат из PE, не проверяя, что подпись действительна и покрывает
файл целиком — единственной реальной привязкой оставался sha256 из
того же релиза.

**Исправлено**: `VlessTunnel.Native.AuthenticodeVerifier.IsValidlySigned`
— настоящая проверка через `WinVerifyTrust`
(`WINTRUST_ACTION_GENERIC_VERIFY_V2`, `WTD_UI_NONE`, `WTD_REVOKE_NONE` —
у самоподписанного сертификата нет точки распространения CRL/OCSP,
проверять отзыв нечем, пересмотреть при переходе на SignPath). Поля и
порядок структур `WINTRUST_DATA`/`WINTRUST_FILE_INFO`
(`Interop/WinTrustTypes.cs`) сверены построчно с документацией
Microsoft (learn.microsoft.com, ns-wintrust-wintrust_data/
ns-wintrust-wintrust_file_info), размеры/смещения перепроверены юнит-
тестами тем же методом, что и для WFP (`WinTrustStructLayoutTests.cs`,

### 5. Выключать ли туннель перед скачиванием — диагноз пересмотрен, подтверждено живьём

Диагноз ревью верен, исходный (записанный на этапе 7) — нет. Проверено
живым тестом (не в теории): включённый туннель + активный kill-switch +
скачивание с `api.github.com` от имени SYSTEM (тот же контекст, что у
самой службы) — `HTTP 200`, без единой ошибки. permit-фильтр kill-
switch'а на TUN-интерфейсе действительно не различает процессы —
изначальная запись "самому процессу службы выйти в интернет нельзя"
была неверна. Настоящая причина исходной ошибки "Хост не обнаружен" —
DNS-баг (TUN-адаптеру не назначался DNS-сервер), исправленный раньше в
этой же сессии (`SetTunDns`) и по времени совпавший с добавлением
"выключать перед скачиванием", отсюда и неверный вывод.

**Исправлено**: и `UpdateCoreAsync`, и `self-update`
(`IpcServer`→`SelfUpdater.CheckAndRunAsync`, колбэк `turnOffTunnelAsync`)
теперь выключают туннель только НЕПОСРЕДСТВЕННО перед подменой файлов
(`xray.exe` — EXE-образ работающего процесса, его нельзя перезаписать,
пока процесс жив — выключение осталось необходимым, просто переехало к
месту, где оно физически нужно) — не перед скачиванием. Реальная
причина, по которой это важно (не ради красоты): если весь остальной
интернет пользователя, кроме самого туннеля, недоступен (цензурируемая
сеть) — старое поведение делало `update-core`/`self-update`
невозможными в принципе; если доступен, но через прокси/другой канал —
пользователь на время скачивания (может быть много мегабайт) оставался
без интернета целиком без необходимости.

**Побочная находка живым тестом** (не входила в диагноз ревью, но
обнаружилась при живой проверке фикса): первый прогон нового порядка
упал на `File.Copy` с "используется другим процессом" — `TryKillXray`
вызывал `Process.Kill(entireProcessTree: true)` БЕЗ `WaitForExit()`
после — `Kill()` асинхронен на уровне ОС, не гарантирует, что процесс
успел выйти и отпустить свой EXE-файл к моменту возврата. Гонка была
всегда, просто маскировалась большим временны́м запасом между
выключением (в самом начале) и подменой файлов (после скачивания) в
СТАРОМ порядке — новый порядок её обнажил. Исправлено: `TryKillXray`
теперь ждёт `WaitForExit(5000)` после `Kill()`, с логом-предупреждением
при таймауте (не исключением — сохраняет прежнюю best-effort семантику
teardown-шагов).

**Проверено живьём**: полный цикл `on` → `update-core` (сервисный
`HttpClient` реально проксируется через сам туннель — в логе видно
`tun-in -> proxy` на IP GitHub во время скачивания, туннель не
выключался) → успешное обновление ядра → туннель автоматически вернулся
в `On`. До фикса гонки (`TryKillXray`) тот же сценарий падал на
`File.Copy`; после — стабильно проходит. Живой тест на своём стенде
попутно наткнулся на уже известное с более раннего этапа этой же сессии
зависшее состояние драйвера Wintun (снялось только `virsh reset`,
полным сбросом, не мягкой перезагрузкой) — это загрязнение стенда от
интенсивного тестирования, не относится к продукту.

### 6. sc stop не дожидается остановки службы, doctor стоял перед ним — подтверждено, исправлено

Диагноз верен на оба пункта: `Exec(sc.exe stop, ewWaitUntilTerminated)`
ждёт завершения ПРОЦЕССА `sc.exe` (доли секунды), а не факта остановки
самой СЛУЖБЫ — она останавливается асинхронно; и в `[UninstallRun]`
`doctor` (снимает WFP-фильтры) стоял ДО `sc.exe stop`.

**Исправлено**: добавлена `WaitForServiceStopped` — опрашивает реальное
состояние через сам Win32 API (`OpenSCManagerW`/`OpenServiceW`/
`QueryServiceStatus` из advapi32.dll напрямую, не парсинг текста
`sc query` — тот локализован по меткам полей, тот же урок, что и в
`GetExistingAllowUser`/ревью п.1). `StopExistingService` (апгрейд поверх)
теперь ждёт до 30с и прерывает установку явной ошибкой при таймауте —
раньше копирование файлов могло начаться раньше, чем процесс реально
освободил свой exe. Деинсталляция: `doctor`/`sc stop`/`sc delete`
перенесены из декларативного `[UninstallRun]` (не поддерживает ожидание)
в Pascal-процедуру `StopAndCleanupServiceForUninstall`, вызывается из
`CurUninstallStepChanged(usUninstall)` — теперь строго `stop` → дождаться
→ `doctor` → `delete`, не наоборот.

**Проверено живьём**: полный цикл переустановки (апгрейд поверх — не
падает, `StopExistingService` проходит) и полного удаления (`unins000.exe
/VERYSILENT`) — чисто, служба удалена, папка пуста (не считая случайного
мусора от ручных тестовых деплоев этой же сессии — не имеет отношения к
установщику, `.pdb` никогда не входят в `[Files]`). Дополнительно
прогнана деинсталляция сразу после попытки `on` — без ошибок, за 2.1с,
служба корректно удалена, обычный интернет без туннеля работает
(`200 OK`), `rescue.ps1` в конце нашёл 0 WFP-фильтров.

**Не до конца показательно**: в этом прогоне `on` сама не удалась (то же
знакомое по сессии зависшее состояние драйвера Wintun на стенде — адаптер
не поднялся за 40с, `State: Error`), а `KillSwitch.Install` в коде стоит
ПОСЛЕ `WaitForAdapterAsync` (`TunnelManager.cs:123` и `:174`) — то есть
фильтры в этом конкретном прогоне, скорее всего, вообще не успели
встать, и "0 фильтров после" ничего не доказывает про порядок
doctor/stop сам по себе (могло быть 0 и без фикса). Корректность самого
порядка (`stop` → дождаться → `doctor`) подтверждена по коду и тем, что
обычный цикл переустановки/удаления проходит без ошибок и таймаутов —
но живого теста именно "doctor снимает РЕАЛЬНО ЖИВЫЕ фильтры уже
остановленной, а не работающей службы" на этом стенде получить не
удалось из-за независимой проблемы с адаптером. Не критично: сама смена
порядка — правка, не рискующая ничем хуже старого поведения, даже если
это конкретное свойство не подтверждено живым тестом с настоящими
фильтрами.

### 7. RunNetsh повторяет уже пойманный pipe-баг — подтверждено, исправлено

Диагноз верен буквально: `RedirectStandardOutput`/`RedirectStandardError`
оба включены, но НИ ОДИН поток не читался до `WaitForExit(5000)` — netsh
мог заблокироваться на записи в заполненный pipe-буфер, если его никто
не читает (тот же класс бага, что уже ловили на `xray.exe`), а
`p.ExitCode` дальше читался без проверки, что `WaitForExit` вообще
дождался — на процессе, который всё ещё жив, это бросило бы
`InvalidOperationException` прямо посреди `StartAsync`.

**Исправлено**: `RunNetshAsync` — `StandardOutput`/`StandardError`
вычитываются `ReadToEndAsync()` ПАРАЛЛЕЛЬНО ожиданию (не после), ожидание
— через `WaitForExitAsync` с `CancellationTokenSource(5с)`, таймаут
явно логируется и процесс убивается, а не тихо продолжает выполнение с
непроверенным `ExitCode`. `SetTunDns`/вызов из `StartAsync` стали
`async`/`await` (был синхронный `void`-путь внутри уже асинхронного
метода).

**Проверено живьём**: полный цикл `on` (два прогона `RunNetshAsync` —
`set dns`+`add dns` — во время `StartAsync`) → `status` → `State: On` без
зависаний и исключений; `netsh interface ip show dns name=xray0`
подтвердил оба DNS-сервера назначены; `test` — `HTTP/SOCKS5/TCP/DNS` все
`OK`. Регрессии в поведении DNS-фикса из более раннего этапа этой же
сессии нет. Первая попытка `on` после свежего `virsh reset` в этом
прогоне поймала уже знакомую по сессии ошибку зависшего Wintun
("Cannot create a file when that file already exists", NTSTATUS
`0xC0000035` = `STATUS_OBJECT_NAME_COLLISION`) — на этот раз даже на
самом первом использовании адаптера после холодной перезагрузки, то
есть не только накопленное за сессию состояние; повторная попытка сразу
после перезапуска службы прошла чисто. Не относится к этому фикса —
`SetTunDnsAsync` вызывается уже ПОСЛЕ `WaitForAdapterAsync`, до фикса
даже не доходило.

### 8. Broadcast блокирует службу — подтверждено, исправлено

Диагноз верен и серьёзен: `Broadcast` писал подписчикам СИНХРОННО
(`StreamWriter.WriteLine`) прямо из `SetState`, который вызывается
ИЗНУТРИ `OnAsync`/`OffAsync` под единственным на всю службу `_gate`
(`SemaphoreSlim(1,1)`, `TunnelController`). Если подписчик (например,
зависший трей) не читает свой конец канала — ОС-буфер именованного
канала заполняется, `WriteLine` блокируется НАВСЕГДА, `_gate` никогда
не освобождается (`finally` с `Release()` не выполняется, пока метод не
вернулся) — то есть один зависший клиент вешал БУКВАЛЬНО ВСЮ СЛУЖБУ для
всех, не только себя.

**Исправлено**: у каждого подписчика теперь своя ограниченная очередь
(`Channel<string>`, capacity 8) и отдельная задача-обработчик
(`DrainSubscriberAsync`), которая читает очередь и пишет в pipe. Сам
`Broadcast` только кладёт событие в очередь через `TryWrite` — эта
операция НИКОГДА не блокируется по определению `Channel`; если очередь
переполнена (подписчик не успевает/не читает вовсе), такой подписчик
немедленно отключается (`Pipe.Dispose()`), а не блокирует всех
остальных.

**Проверено живьём**: открыт сырой pipe-клиент напрямую (`System.IO.
Pipes.NamedPipeClientStream`, в обход обычного CLI), отправлена команда
`subscribe`, дальше подписчик СОЗНАТЕЛЬНО ни разу не читает свой конец
канала (имитация зависшего трея) — и оставлен подключённым на всё
время теста. Параллельно с ЭТИМ же зависшим подписчиком с другого,
нормального клиента несколько раз подряд вызван `toggle` (каждый
реально проходит через `SetState`→`Broadcast` минимум дважды) — все
вызовы завершились быстро (0.86-2.28с) кроме одного, упёршегося в уже
известный по этой сессии таймаут ожидания адаптера Wintun (40.5с, не
связано с этим фиксом, тот же класс проблемы, что и в пунктах 6-7).
Ни одного признака бесконечного зависания из-за неотвечающего
подписчика — именно то, что было бы гарантированно с исходным кодом.

### 10. Служба не восстанавливает состояние туннеля после перезапуска — подтверждено, исправлено

Диагноз верен: `OnStart` поднимал только IPC, туннель всегда стартовал
в `Off`, желаемое состояние нигде не хранилось — при этом постоянные
WFP-фильтры переживают и падение процесса, и перезагрузку (doc-
комментарий `KillSwitch`), так что `sc failure` (этап 3.9) перезапускал
упавшую службу, но не туннель — сам механизм автовосстановления не
достигал цели, ровно как описано в ревью.

**Исправлено**: `desired-state.txt` в `%ProgramData%\vless-tunnel`
(рядом с `link.txt`) — пишется при каждом успешном явном `on`/`off`
(`TunnelController.SaveDesiredState`). `RestoreDesiredStateAsync`
вызывается один раз при `OnStart`: если желаемое — включено и ссылка
задана, поднимает туннель сам; если выключено (или файла ещё нет,
первый запуск) — прогоняет `KillSwitch.Doctor`, снимая осиротевшие
фильтры, не дожидаясь, пока пользователь заметит пропавший интернет.

**Проверено живьём** через `with-rescue.sh`: туннель включён →
`Stop-Process -Force` по процессу службы (не штатный `sc stop` —
имитация падения/обрыва питания, никакого teardown не происходит) →
`sc failure` поднимает службу заново (`Status: Running` в течение
~15с) → `RestoreDesiredStateAsync` САМ, без единой команды снаружи,
возвращает туннель в `State: On`. Полный цикл `PASS`.

**Побочная находка тем же живым тестом**: первый прогон упал на
`CreateIpForwardEntry2(...) failed` — хост-маршрут до сервера,
добавленный СТАРЫМ (убитым) процессом, остался в таблице маршрутов
(teardown живёт только в памяти процесса, теряется вместе с ним),
новый процесс пытался добавить ТОТ ЖЕ маршрут и падал на дубликате;
`WithRetry` для этого конкретного вызова не спасает — это не гонка с
ОС ("ещё не готова"), а буквально уже существующая запись, которая
сама не денется. Исправлено: `AddHostRoute` теперь сначала best-effort
снимает возможный осиротевший маршрут (`TrySafe`), потом добавляет
свежий. Повторный прогон того же теста после этого фикса — чисто,
без единой ошибки.

**Не проверено отдельным живым тестом**: (а) настоящая перезагрузка
ОС — `Stop-Process -Force` заведомо жёстче (полностью пропускает
`OnStop`/teardown, тогда как штатный reboot обычно даёт службе шанс
на graceful-остановку) — код `OnStart`, который реально проверяется,
идентичен в обоих случаях, поэтому этот тест считаю достаточным
подтверждением; (б) сценарий "желаемое состояние — off, а фильтры уже
есть" отдельно не воспроизведён — по размышлению, его тяжело получить
через обычные последовательности операций (пока процесс жив,
`OffAsync` сам чисто снимает фильтры через штатный `teardown`; чтобы
получить именно "off" в `desired-state.txt" при живых фильтрах, нужна
смерть процесса РОВНО в узком окне между `SetState(Stopping)` и
завершением `SafeStopAsync()`, что не удалось надёжно подстроить) —
сам код-путь (`KillSwitch.Doctor`) уже многократно проверен живьём в
других частях этой сессии (этап "rescue.ps1", деинсталляция).

### 11. Транспорты quic/http принимаются вопреки плану — подтверждено, исправлено

### 12. allowInsecure=1 молча терялся — подтверждено, исправлено

Диагноз верен буквально: `OutboundBuilder` при `CoreFamily=modern`
(дефолт) и `allowInsecure=1` ставит `pinnedPeerCertSha256` ТОЛЬКО если
`options.CertPin` уже задан — а получение самого отпечатка (план, 3.1:
"allowInsecure → получить отпечаток сертификата и прописать
pinnedPeerCertSha256, как cert-pin на Linux") не было реализовано
нигде в решении. Итог — ссылка на самоподписанный сертификат молча
подключалась со строгой проверкой и не работала.

**Исправлено**: `CertPinResolver.ResolveAsync` (Service) — порт
`cmd_cert_pin` из эталона (`~/src/vless-tunnel/vless-tunnel.sh`,
только чтение): TLS-рукопожатие без проверки сертификата (в этом и
смысл — сервер сам по себе самоподписанный), SHA256 от сырых DER-байт
самого сертификата и всей построенной цепочки (дубликаты — один раз),
через запятую — тот же формат, что понимает `pinnedPeerCertSha256` у
Xray. Вызывается из `TunnelController.OnAsync` ДО сборки конфига (сам
`BuildOptions.CertPin` — неизменяемый `init`-параметр, задать позже
нельзя) — только когда `security=tls` и `allowInsecure=1` в ссылке
(REALITY использует своё доверие через pbk/sid, cert-pin ей не нужен).

**Проверено живьём** отдельным консольным инструментом
(`scratchpad/certpin-test`) против настоящего публичного самоподписанного

### 13-14. Событие смены сети терялось безвозвратно / RecomputeHostRoute переживал StopAsync — подтверждено, исправлено

Диагноз ревью подтверждён чтением кода до правки: `OnNetworkChanged`
запускал `Task.Run` на КАЖДОЕ событие со своим `CancellationTokenSource`,
который отменялся следующим событием — при буре событий (реконнект
Wi-Fi, выход из сна, переключение Wi-Fi/Ethernet) пересчёт мог не
выполниться ни разу. Окно подавления эха собственных мутаций
(`_suppressNetworkChangeUntilUtc`) само себя продлевало на каждый
удачный пересчёт (`MarkSelfMutation` внутри `WithRetry`/`TrySafe`),
усиливая проблему. Отдельно, `StopAsync` отменял `_debounceCts`, но уже
проснувшийся пересчёт (токен внутрь него не передавался) ничем не
останавливался и мог добавить хост-маршрут ПОСЛЕ того, как `StopAsync`
его снял.

**Исправлено** (`TunnelManager.cs`): один последовательный воркер
(`NetworkWatchWorkerAsync`) вместо `Task.Run` на событие — события
сигнализируют через `SemaphoreSlim(0,1)` (сам семафор и есть дебаунс:
лишние сигналы схлопываются), обрабатывает их одна задача с токеном,
привязанным к жизни туннеля. `StopAsync` эту задачу ДОЖИДАЕТСЯ
(`await _watchWorkerTask`), а не просто отменяет — после `await`
воркер гарантированно не выполняет и не начнёт выполнять пересчёт,
поэтому `RemoveHostRoute` в `StopAsync` не может наложиться на его же
`AddHostRoute`. Заодно ушла сама возможность гонки из п.14 (два
пересчёта одновременно, один в `WithRetry` до 15 с) — воркер один,
конкурентных пересчётов больше не бывает вообще.

Плюс периодическая идемпотентная сверка (`ReconcileNetworkStateAsync`,
раз в 20 с, независимо от событий) — закрывает и сам п.13 (потерянное
событие подхватит таймер), и требование плана 3.9 ("после сна и
гибернации — полная проверка, не только по уведомлениям"): хост-маршрут
(не через TUN), /1-маршруты, адрес(а) TUN, DNS адаптера — каждая
проверка сама решает, чинить ли что-то, безопасно звать на каждый тик.
Окно подавления эха осталось, но теперь это фильтр ТОЛЬКО для
событийного пути внутри воркера (пропускает один прогон), периодический
тик его не спрашивает вовсе — ревью явно предупреждало не потерять
сверку из-за этого окна.

Отдельная находка живым тестом (не было в ревью): после гибели xray.exe
не через `StopAsync` (сам процесс упал/убит) TUN-адаптер пропадает
вместе с ним, а `_tunIfIndex` продолжает указывать на несуществующий
интерфейс — три TUN-зависимые сверки (сплит-маршруты/адрес/DNS)
обёрнуты в свой `try/catch` (`Win32Exception`), чтобы это не мешало
хост-маршруту (не завязан на TUN) продолжать поддерживаться. Отдельную
проверку "жив ли адаптер" завести не получилось надёжно —
`NetworkInterface.GetAllNetworkInterfaces()` и
`ConvertInterfaceIndexToLuid` оба живым тестом пойманы на ложном "жив"
для уже погибшего `ifIndex`; решили не гадать, а просто ловить исключение
на месте.

**Проверено живьём** (`vt-win10`, живой стенд):
- самоисцеление хост-маршрута: руками снесён `route delete` на живом
  туннеле — восстановлен в течение одного цикла периодической сверки
  (~20 с), без единого сетевого события; жёсткий инвариант

  продолжает поддерживаться, TUN-зависимые сверки падают тихо (ни
  краха, ни шторма повторов, ни единой лишней строки в логе за 90+ с

- НЕштатное убийство самого процесса службы (`Stop-Process -Force`) при

### 16. Два писателя в один StreamWriter (IpcServer) — подтверждено, исправлено

### 17. Перерезолв ломается о round-robin — подтверждено, исправлено

Диагноз подтверждён чтением кода: `PeriodicReresolveLoopAsync` сравнивал
новый адрес с `_serverIp`, а `BootstrapResolver.ResolveAsync` берёт

совсем.

**Только тестами**: `dotnet test` зелёные; живой тест с реальным
round-robin хостом не проводился (нужен хост с несколькими A-записями
под контролем, `ReresolveInterval` — 10 минут, не переопределяется
снаружи для теста) — риск минимальный (чистая логика сравнения с
множеством вместо одного элемента), но не подтверждён вживую.

### 18. certPin == null всё равно поднимал туннель — подтверждено, исправлено

Диагноз подтверждён чтением кода: при неудачном `CertPinResolver.ResolveAsync`

### Нестабильность wintun-адаптера (~30-40% отказов при быстром off→on) — диагностировано, исправлено

Ещё в разделе про 13-14 было честно записано как известная, не
проверенная до конца находка: быстрый цикл on/off даёт "Адаптер
\"xray0\" не поднялся за 40с" примерно в трети случаев, одинаково что
на старом, что на патченном (на тот момент) коде — то есть не
регрессия, а давно существующий класс проблемы. По просьбе владельца
разобрано отдельно.

**Диагноз**: xray.exe в момент отказа умирает САМ, куда раньше нашего
40-секундного таймаута ожидания (~15с) — `xray[err]` показывал `Failed
to setup adapter`/`Cannot create a file when that file already exists`.
`TryKillXray` у ПРЕДЫДУЩЕГО запуска убивает xray.exe через `Kill()`
(жёстко, `TerminateProcess`) — процесс не успевает штатно закрыть свою
сессию wintun. `Get-PnpDevice` подтвердил: PnP-объект адаптера
(`SWD\WINTUN\{...}`) переживает цикл off→on с ТЕМ ЖЕ `InstanceId`, в
отличие от сетевого интерфейса (тот пропадает из `Get-NetAdapter`
почти мгновенно) — то есть на уровне драйвера что-то остаётся
занятым дольше, чем видно через обычные сетевые API, и следующий
xray.exe, пытаясь пересоздать адаптер с тем же именем, изредка на это
натыкается. Ждать дольше (как это неявно делал старый код, тратя
оставшиеся ~25с бесполезного опроса после того, как xray.exe уже
мёртв) — не помогает: гонка транзиентная, но проходит только с новой
попыткой запуска, не с более долгим ожиданием уже упавшего процесса.

**Исправлено** (`TunnelManager.cs`): `WaitForAdapterAsync` получил сам
процесс `xray.exe` и, если тот успел выйти раньше поднятия адаптера,
сразу бросает `XrayExitedEarlyException` (быстрый явный отказ вместо
бесполезного досиживания оставшегося таймаута). Новый
`LaunchXrayAndWaitForAdapterAsync` оборачивает запуск xray.exe в цикл
до 3 попыток: поймал `XrayExitedEarlyException` — откатывает именно
эту (последнюю) неудачную попытку (`RetireFailedXrayAttempt`, не
трогая ничего из накопленного раньше в `_teardown`), ждёт 2с и
запускает xray.exe заново. Настоящий зависший процесс (обычный
`TimeoutException`, xray.exe не умер, просто адаптер не появился) НЕ
повторяется — там повтор ничего не даст, а вот повторный запуск того
же самого зависшего процесса только удвоил бы бесполезное ожидание.

**Проверено живьём**: 20 циклов on/off подряд тем же способом, что и
базовая линия в разделе 13-14 — **0/20 отказов** (было 7/20 на
патченном коде и 9/20 на старом при том же тесте). В логе — 8 срабатываний
повтора за 20 циклов (`xray.exe завершился раньше поднятия адаптера
(попытка 1/3, ...) - ... код выхода 23. Повтор через 2с`), после
каждого — успешный второй запуск; по времени выполнения `on` виден тот
же паттерн: без гонки — 0.8-2.3с, с одним повтором — 18-19.5с (~15с
на упавшую попытку xray.exe + 2с паузы + быстрый успешный повтор).
Маршрутная таблица и адаптер после всех 20 циклов — чисто, осиротевших
записей нет.

### 22. GetBestGateway при поднятом туннеле ВСЕГДА возвращает TUN — подтверждено, исправлено

Диагноз подтверждён живым тестом до правки, ещё на коде из раздела
13-14: ручное снятие хост-маршрута на поднятом туннеле СТАБИЛЬНО, не
изредка, давало в логе "Пересчёт шлюза вернул сам TUN". Механика ровно
та, что описал аудит: пока туннель поднят, в таблице есть 0.0.0.0/1 и
128.0.0.0/1 через TUN; Windows выбирает маршрут сначала по длине
префикса, `GetBestRoute2` без ограничения интерфейсом (`interfaceIndex=0`)
для ЛЮБОГО адреса (включая сам сервер, как только его /32 снят перед
пересчётом) находит /1 длиннее физического /0-default и возвращает TUN —
не как редкий сбой, а на каждом прогоне. Старый "жёсткий инвариант" (`if
newIfIndex == _tunIfIndex`) поэтому был не страховкой от редкой гонки, а
ЕДИНСТВЕННЫМ работающим путём: реальная смена сети не детектировалась
никогда, пока туннель включён. Комментарий в коде, объяснявший это
"задержанным событием NLA", был неверен — переписан на структурную
причину.

**Исправлено** (`RouteManager.cs`, `TunnelManager.cs`):
- `GetBestRoute2` теперь вызывается с ЯВНЫМ `interfaceIndex`
  (`GetBestRouteOnInterface`) — параметр был в объявлении и раньше,
  просто не использовался; с ним TUN физически не может попасть в
  ответ, раз не является запрошенным интерфейсом;
- `FindBestPhysicalGateway` перебирает поднятые физические интерфейсы
  (TUN исключён явно) с IPv4-шлюзом, для каждого спрашивает
  `GetBestRouteOnInterface` — нашёлся маршрут именно на нём, это
  кандидат; между кандидатами выбор — как сама Windows, по минимальной
  сумме метрики маршрута и метрики интерфейса

  новый P/Invoke, самая большая структура в проекте — разметка взята
  дословно из документации Microsoft, не по памяти, обязательный
  `NativeStructLayoutTests` на размер/смещения);

**П.20 (заодно, поглощён этой же правкой)**: `WithRetry` получил токен

### 21. Повтор запуска xray лечит симптом, а не причину — подтверждено, исправлено другим путём

Диагноз аудита подтверждён собственным же коммитом (13-14/wintun):
каждое третье включение после быстрого выключения стоило ~19с вместо
~1с (15с на падающую попытку xray.exe + 2с паузы) — жёсткий `Kill()`
предыдущего процесса не даёт ему штатно закрыть сессию wintun, и
коллизия "file already exists" при пересоздании адаптера С ТЕМ ЖЕ
ИМЕНЕМ изредка возникает.

**Основной путь аудита не пошёл в реализацию — по здравой оценке риска,
не по недостатку попытки.** `CTRL_BREAK` перед `Kill()` требует
`CREATE_NEW_PROCESS_GROUP`, которого нет в `ProcessStartInfo` — его
пришлось бы добавлять через сырой `CreateProcess` в обход
`Process.Start()` целиком, ЗАОДНО переписывая ручную настройку stdout/
stderr pipe'ов (сейчас это делает `Process.Start`/`BeginOutputReadLine`
из коробки). `CreateNoWindow=true` у xray.exe сейчас означает не
"скрытая консоль", а ОТСУТСТВИЕ консоли вовсе (документированное
поведение `CREATE_NO_WINDOW`) — без своей консоли/process group к
процессу нельзя привязаться и отправить консольное событие, не рискуя
задеть саму службу, если попытаться завести общую консоль. Поверх
этого — непроверяемое допущение: отреагирует ли рантайм Go внутри
xray-core на такой сигнал штатным закрытием wintun-сессии вообще, без
чтения его исходников. Риск (переделка запуска ядрового процесса
службы) явно не окупался неопределённой выгодой — решено сразу пойти
по alternативe, которую тот же аудит прямо разрешил.

**Исправлено** (`TunnelManager.cs`, `CloneWithOutbound`/
`ChooseTunAdapterName`): имя TUN-адаптера чередуется между
`<configured>` и `<configured>b` (статический счётчик, переживает
пересоздание `TunnelManager` между on/off) — если предыдущий адаптер
того же имени ещё не до конца освобождён ОС, новому просто не с чем
сталкиваться, коллизия устраняется МЕХАНИЧЕСКИ, без каких-либо ставок
на поведение xray-core. Kill-switch (`KillSwitch.Install`) и так был
завязан на `tunInterfaceIndex`, не на имя — пережил проверку без
единой правки. `ConfigBuilder` просто прокидывает переданное имя
дальше, тоже без правок.

**Проверено живьём**: те же 20 циклов on/off, что и в разделе про
wintun-нестабильность (эта же сессия) — **0 циклов дольше 5с** (было
примерно половина по 18-19.5с), максимум 2.05с, минимум 0.84с; 0/20
отказов; в логе имя чисто чередуется на каждом цикле (`xray0`
ifIndex=13 → `xray0b` ifIndex=33 → `xray0` → ...); маршрутная таблица и
адаптер после прогона — чисто, осиротевших записей нет. Обновлён и
`tests/vm/scenarios/on-off-cycle.ps1` (проверяет оба возможных имени
адаптера, не только `xray0`).

**Только тестами**: `dotnet test` зелёные (88 шт., без изменений в
покрытии — это чисто рантайм-поведение, не тестируемое юнитами).
