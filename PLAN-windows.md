# vless-tunnel для Windows — план реализации

Задача для агента. Сделать нативный клиент для Windows 10/11 по образцу
Linux-версии [RamDll/vless-tunnel](https://github.com/RamDll/vless-tunnel)
(эталон — v1.2.9). Переносится **поведение**, а не код: bash, iptables,
systemd и sudoers в Windows заменяются аналогами ниже.

Главное требование владельца: ссылки с post-quantum параметрами
(`encryption=mlkem768x25519plus…`, REALITY `pqv`) должны работать так же,
как на Linux и на роутере. Из-за них чужие клиенты не подходят.

---

## 1. Стек и решения

| Что | Решение |
|---|---|
| Язык | C#, **.NET 10 (LTS)**. .NET 8 не брать: поддержка заканчивается в ноябре 2026 |
| Цели | Windows 10 22H2 x64 и Windows 11 x64. ARM64 позже |
| Публикация | self-contained, `PublishSingleFile`, без требования ставить рантайм |
| Ядро | официальный `xray.exe` + `wintun.dll` из релиза XTLS/Xray-core (win-64 zip), версия закреплена, sha256 сверяется |
| Перехват | TUN-инбаунд Xray (Wintun) + маршруты, которые ставит служба |
| Привилегии | Windows-служба от LocalSystem; GUI и CLI без UAC, через named pipe |
| Установщик | Inno Setup (`.exe`), собирается в GitHub Actions (`windows-latest`) |
| GUI | WinForms: значок в трее + главное окно |

Не делаем (сознательно):
- legacy-транспорты `type=quic` / `type=http` (ядро v1.8.24): в нём нет TUN-инбаунда. Такая ссылка → понятная ошибка;
- режим шлюза для других устройств LAN;
- выборочную маршрутизацию по спискам доменов (возможно, позже: на Linux её тоже нет, это полный туннель);
- Windows 7/8.

## 2. Структура решения

```
src/
  VlessTunnel.Core/      разбор ссылки, сборка config.json, модели, общие константы
  VlessTunnel.Service/   служба: Xray, TUN, маршруты, kill-switch, DNS, watchdog, IPC-сервер
  VlessTunnel.Cli/       vless-tunnel.exe — команды через IPC
  VlessTunnel.Tray/      трей + окно, клиент IPC
  VlessTunnel.Native/    P/Invoke: IP Helper (iphlpapi), WFP (fwpuclnt)
tests/
  VlessTunnel.Core.Tests/   юнит-тесты + golden-тесты паритета с Linux
  parity/                   ссылки и эталонные JSON из Linux-бэкенда
installer/
  vless-tunnel.iss
.github/workflows/
  build.yml                 сборка, тесты, установщик, релиз по тегу
```

Пути на машине:

| Что | Где |
|---|---|
| Программа | `%ProgramFiles%\vless-tunnel\` (exe, xray.exe, wintun.dll) |
| Конфиг и ссылка | `%ProgramData%\vless-tunnel\` — ACL только SYSTEM + Administrators (в ссылке секретный UUID) |
| Сгенерированный config.json | там же, пересобирается при каждом старте |
| Логи | `%ProgramData%\vless-tunnel\logs\` с ротацией + Event Log для службы |

## 3. Архитектура

### 3.1 Разбор ссылки и config.json (Core)

Портировать Python-бэкенд из `vless-tunnel.sh` (функции `parse`/`make`,
примерно строки 290–760) **один в один**:

- транспорты: `tcp`/`raw`, `ws`, `grpc` (+`mode=multi`), `httpupgrade`, `xhttp`/`splithttp` (+`mode`, `extra` как JSON), `kcp` без header/seed;
- REALITY: `pbk`, `sid`, `spx`, `fp`, **`pqv` → `mldsa65Verify`**;
- TLS: `sni`, `fp`, `alpn`, `ech`; `allowInsecure` → получить отпечаток сертификата и прописать `pinnedPeerCertSha256` (как `cert-pin` на Linux);
- **`encryption=`** передаётся в `users[].encryption` без изменений;
- `flow=xtls-rprx-vision` → клиентский `xtls-rprx-vision-udp443` (опция отключения);
- IPv6-хост в `[...]`, ссылка без схемы, многострочная вставка с разрывами.

Отличия от Linux в config.json:
- инбаунд `tun` вместо `dokodemo-door` + TPROXY;
- SOCKS5 `127.0.0.1:10808` (с UDP) и HTTP `127.0.0.1:10809` — как на Linux;
- **адрес сервера в `vnext` — уже разрешённый IP** (см. 3.2), SNI/Host остаются доменом;
- правило `port 53 → dns-out`, DNS Xray — DoH через туннель;
- приватные сети → `direct` (опция `--proxy-lan` отключает).

**Паритет обязателен** (порядок работы — 5.7). Golden-тесты: набор ссылок (включая PQ, REALITY+pqv,
XHTTP+extra, vision, IPv6-хост, битые ссылки) прогоняется через Linux-бэкенд
(`vless-tunnel.sh`, подкоманда `make`), эталонные JSON коммитятся в
`tests/parity/`. C#-сборщик должен давать тот же outbound-блок байт в байт
(после нормализации JSON). Инбаунды сравниваются отдельно.

### 3.2 Перехват трафика и петля (Service)

Встроенный TUN Xray только поднимает адаптер. Адреса, маршруты и правила
делает ОС, то есть служба. Индекс интерфейса меняется при каждом запуске
Xray, поэтому ищем его заново каждый раз.

Порядок старта:
1. **Bootstrap-резолв** домена сервера самой службой (системный резолвер, до поднятия TUN). IP подставляется в config.json. Прямой DNS-исходящий Xray для bootstrap не нужен.
2. Запомнить текущий физический интерфейс и шлюз по умолчанию (`GetBestRoute2`).
3. Запустить `xray.exe` (Job Object: при смерти службы умирает и Xray).
4. Дождаться адаптера (`GetAdaptersAddresses`, по имени из конфига), таймаут.
5. Назначить адрес TUN (`CreateUnicastIpAddressEntry`), например `172.19.0.1/30`; для IPv6 — ULA из `fd00::/8` (без маршрутизируемого адреса IPv6 через TUN не пойдёт).
6. Маршруты (`CreateIpForwardEntry2`):
   - хост-маршрут до IP сервера через физический шлюз — **это и есть защита от петли** для proxy-исходящего;
   - `0.0.0.0/1` и `128.0.0.0/1` через TUN (не трогаем штатный default route);
   - IPv6: `::/1` и `8000::/1` через TUN, либо блок IPv6 при `--block-ipv6`;
   - приватные сети остаются на физическом интерфейсе (более специфичные маршруты выигрывают).
7. DNS: DNS-сервер адаптера TUN = адрес внутри TUN, низкая метрика TUN.
8. Включить kill-switch (3.3).

Отслеживать `NotifyRouteChange2` / `NotifyIpInterfaceChange` (смена Wi-Fi,
переподключение кабеля, сон): пересчитать физический шлюз и переставить
хост-маршрут до сервера. Периодически перерезолвить домен сервера; при
смене IP — перезапуск.

Остановка — строго в обратном порядке. Все созданные маршруты и фильтры
помечаются и снимаются по метке, не «по памяти процесса».

### 3.3 Kill-switch (обязателен)

На Linux kill-switch получается «по построению». **На Windows — нет:** если
Xray упал, адаптер TUN исчезает вместе с маршрутами, и трафик молча уходит
напрямую. Поэтому kill-switch через WFP — часть MVP, а не опция.

WFP, свой provider + sublayer с высоким весом, **постоянные** (не dynamic)
фильтры, чтобы пережить падение службы:
- разрешить: `xray.exe` (по app id), интерфейс TUN, loopback, DHCP, приватные сети (если не `--proxy-lan`);
- запретить: всё остальное исходящее, IPv4 и IPv6;
- DNS-утечки: запретить порт 53 на всех интерфейсах, кроме TUN (Windows параллельно шлёт DNS во все интерфейсы).

Снимаются фильтры только явным `off` или `uninstall`. `doctor` должен
уметь их найти и снять («аварийный выключатель» на случай поломки).

### 3.4 IPC и права (аналог sudoers)

Named pipe `\\.\pipe\vless-tunnel`, ACL: SYSTEM, Administrators и
пользователь, указанный при установке (аналог `--allow-user`). Протокол —
JSON-строки: запрос/ответ + **подписка на события** (смена состояния). Трей
не опрашивает службу по таймеру (урок Linux-версии, где опрос раз в 5 с
давал сотни вызовов).

### 3.5 CLI (`vless-tunnel.exe`)

Те же команды, что на Linux, где применимо:

```
on | off | toggle | restart
status [--json]
test            HTTP, SOCKS5, прозрачный TCP, UDP/QUIC, DNS (включая проверку утечки)
logs [--lines N]
set-link [--stdin]
autostart on|off
update-core     скачать релиз Xray, сверить .dgst, откат при неудаче
doctor          окружение + вердикт + снятие зависших WFP-фильтров
ensure          переставить маршруты/фильтры
uninstall [--keep-config]
```

Таймауты клиента IPC должны быть **больше** худшего пути команды в службе
(урок Linux: `toggle` с таймаутом 30 с при пути `on` > 31 с).

### 3.6 Трей и окно

- значок: вкл / выкл / неизвестно (иконки из `packaging/icons` Linux-версии);
- меню: включить/выключить, статус, вставить ссылку, логи, выход;
- окно: ссылка (поле скрывает UUID), статус, кнопка «Проверить», журнал;
- автозапуск трея — ярлык в Startup для пользователя;
- ошибки показывают и stdout, и stderr (урок Linux: `out or err` прятал stderr).

### 3.7 Установщик (аналог .deb)

- ставит файлы, регистрирует службу (автозапуск по опции), ярлыки, трей;
- **обновление поверх**: остановить службу → заменить файлы → запустить; конфиг сохраняется;
- один путь к бинарнику, никаких копий (урок Linux: дубль `/usr/bin` и `/usr/local/bin`);
- `uninstall` из CLI не удаляет файлы, принадлежащие установщику, а только сбрасывает настройку; полное удаление — через «Программы и компоненты»;
- удаление снимает службу, маршруты и WFP-фильтры;
- версия Xray и wintun зашиты в сборку, sha256 проверяется в CI.

### 3.8 Подпись и доверие (самоподписанный сертификат)

Порядок на машине пользователя:
1. `trust.ps1` (один раз, от администратора): сверяет отпечаток `vless-tunnel.cer` с зашитым в скрипт, ставит сертификат в `LocalMachine\Root` и `LocalMachine\TrustedPublisher`, снимает метку «из интернета» (`Unblock-File`) с установщика и запускает его.
2. Установщик: установка или обновление поверх. Повторно `trust.ps1` не нужен.
3. Удаление через «Программы и компоненты» убирает всё, включая сертификат; настройки — по вопросу (см. ниже).

Сертификат: `New-SelfSignedCertificate -Type CodeSigningCert` (только подпись
кода). `.pfx` хранится только в секретах GitHub Actions и в офлайн-копии,
никогда не в репозитории. Подписываются все свои `.exe` и установщик
(директива `SignTool` в Inno Setup, включая деинсталлятор), всегда с меткой
времени (`/tr … /td SHA256`).

Деинсталлятор (Inno Setup):

```ini
[UninstallRun]
; настройки удаляет сам деинсталлятор по ответу пользователя, CLI их не трогает
Filename: "{app}\vless-tunnel.exe"; Parameters: "uninstall --keep-config"; Flags: runhidden waituntilterminated; RunOnceId: "Purge"
Filename: "{sys}\certutil.exe"; Parameters: "-delstore Root <THUMBPRINT>"; Flags: runhidden; RunOnceId: "DelRoot"
Filename: "{sys}\certutil.exe"; Parameters: "-delstore TrustedPublisher <THUMBPRINT>"; Flags: runhidden; RunOnceId: "DelTP"

[UninstallDelete]
; логи удаляются всегда
Type: filesandordirs; Name: "{commonappdata}\vless-tunnel\logs"

[Code]
var
  DeleteSettings: Boolean;

procedure CurUninstallStepChanged(CurUninstallStep: TUninstallStep);
begin
  case CurUninstallStep of
    usUninstall:
      begin
        { тихое удаление (/SILENT, /VERYSILENT) настройки сохраняет }
        DeleteSettings := False;
        if not UninstallSilent() then
          DeleteSettings := MsgBox(
            'Удалить настройки vless-tunnel (ссылку на сервер и параметры)?' + #13#10 + #13#10 +
            'Нет — настройки останутся и подхватятся при следующей установке.',
            mbConfirmation, MB_YESNO or MB_DEFBUTTON2) = IDYES;
      end;
    usPostUninstall:
      if DeleteSettings then
        DelTree(ExpandConstant('{commonappdata}\vless-tunnel'), True, True, True);
  end;
end;
```

Требования:
- вопрос задаётся после подтверждения удаления и до снятия файлов; по умолчанию выбран «Нет»;
- обновление поверх деинсталлятор не запускает — сертификат и настройки не трогаются; обновление через «удалить → поставить» не делать;
- при установке служба подхватывает существующий `%ProgramData%\vless-tunnel`, если он остался;
- один сертификат — один проект: удаление снимает доверие со всего, что им подписано;
- при смене сертификата (истёк срок) — новый `trust.ps1` с новым отпечатком; старые сборки остаются валидными благодаря метке времени.

Известное: даже подписанный файл, скачанный из интернета, SmartScreen может
показывать с предупреждением (проверка по репутации), поэтому `trust.ps1`
снимает метку `Unblock-File`. Прокси-клиенты иногда ложно ловит антивирус.

### 3.9 Эксплуатация: то, что легко упустить

**Аварийное восстановление сети.** Постоянные WFP-фильтры переживают всё,
в том числе ручное удаление папки программы. Если `vless-tunnel.exe` уже нет,
`doctor` не запустить, и машина остаётся без интернета. Поэтому:
- фильтры создаются с фиксированным GUID провайдера и sublayer (константы в Core);
- отдельный самодостаточный `rescue.ps1` (P/Invoke через `Add-Type`, без зависимостей от программы) снимает всё по этим GUID; лежит в репозитории, ссылка — в README и в меню «Пуск»;
- ярлык «Аварийно отключить vless-tunnel» в меню «Пуск».
Альтернатива WFP — правила брандмауэра Windows (снимаются штатным
`Remove-NetFirewallRule`), но они не работают, если сторонний антивирус
подменил брандмауэр. ~~Выбор сделать на этапе 0.~~ Решено на этапе 0б:
**WFP** — переживает замену брандмауэра антивирусом и падение службы
(постоянные фильтры), обычные правила брандмауэра — нет. Подробности и
обоснование — `docs/spike.md`.

**Captive portal** (Wi-Fi в гостинице, кафе). Kill-switch не пустит на
страницу входа. Нужна команда/пункт трея «Пустить на 5 минут напрямую»:
временно снимает блокировку, по таймеру возвращает, туннель не включён.

**Обновление поверх.** Файлы заняты работающими службой и треем. В
`PrepareToInstall` (Inno Setup) остановить службу и закрыть трей всех
пользователей, после установки запустить обратно. Kill-switch на время
обновления остаётся включённым, если туннель был включён.

**Обновление программы (`self-update`).** Проверка релизов на GitHub,
скачивание установщика, сверка sha256 **и** отпечатка подписи с зашитым,
запуск установщика тихо (`/VERYSILENT` — настройки сохраняются, см. 3.8).

**Смена сертификата.** `trust.ps1` содержит список старых отпечатков и
удаляет их из `Root`/`TrustedPublisher` при установке нового. Деинсталлятор
удаляет текущий и все старые.

**Запуск `trust.ps1`.** Скачанный `.ps1` сам помечен «из интернета», а
политика выполнения по умолчанию запрещает скрипты. Нужна обёртка
`install.cmd`: `powershell -NoProfile -ExecutionPolicy Bypass -File "%~dp0trust.ps1"`.

**Кодировка.** Windows PowerShell 5.1 читает `.ps1` без BOM как ANSI —
кириллица в сообщениях превратится в мусор. Все `.ps1` — **UTF-8 с BOM**
(проверка в CI). CLI выставляет `Console.OutputEncoding = UTF8`.

**Секреты в выводе.** UUID и ключи не печатаются в логах, `status`, `doctor`
и окне (маскировать). Конфиг-директория с ACL (3.2 / раздел 2).

**Устойчивость службы.** Действия при сбое (`sc failure`): перезапуск
через 5 с, 30 с, 60 с. Xray в Job Object. После сна и гибернации — полная
проверка маршрутов и адаптера, не только по уведомлениям.

**Время.** REALITY и TLS ломаются при сбитых часах (часто в виртуалках).
`doctor` сверяет время (NTP или заголовок `Date` через туннель) и
предупреждает.

**MTU.** TLS + XHTTP добавляют накладные расходы; MTU TUN 1500 может давать
фрагментацию и «висящие» сайты. Подобрать значение на этапе 0 (ориентир
1400), сделать опцией.

**Совместимость** (аналог раздела в Linux README). Проверить и описать:
другой VPN/TUN (v2rayN, WireGuard, OpenVPN), WSL2, Hyper-V, Docker Desktop
(их трафик идёт через NAT хоста — туннелируется ли и не режет ли его
kill-switch), сторонний антивирус с собственным брандмауэром.

**Лицензии.** `THIRD_PARTY_LICENSES/` как в Linux-репозитории: Xray-core
(MPL-2.0), Wintun (лицензия на готовые бинарники), .NET-зависимости.
Установщик кладёт их в `{app}`.

**Windows 10.** Плановая поддержка закончилась в октябре 2025 года —
основной целью считать и Windows 11, тестировать на обеих.

## 4. Этапы и критерии приёмки

Каждый этап — отдельный PR. Тестирование — на стенде из раздела 5;
опасные тесты — только через `with-rescue.sh`.

**Этап 0а. Стенд.** Виртуалка `vt-win10` создаётся скриптом без участия человека; SSH по ключу и guest agent работают; снимок `clean` есть; `rescue.ps1`, `run-test.ps1`, `with-rescue.sh` готовы; цепочка спасения проверена: намеренно отрезанная сеть возвращается через guest agent, а при «мёртвом» guest agent — откатом снимка.

**Этап 0б. Спайк (без C#, PowerShell).** Это ворота для всего остального. Все эксперименты — через `with-rescue.sh`.
- `xray.exe` + `wintun.dll` + TUN-инбаунд поднимают адаптер;
- ручные маршруты по 3.2 → трафик идёт через сервер, петли нет;
- тестовая ссылка с PQ-параметрами работает;
- проверить IPv6 через TUN с ULA-адресом;
- проверить, как ведёт себя система при `taskkill` Xray (подтвердить утечку без kill-switch);
- выбрать механизм kill-switch: WFP или правила брандмауэра (3.9), проверить способ аварийного снятия;
- подобрать MTU TUN;
- проверить сон/гибернацию и смену Wi-Fi ↔ кабель.
Результат — `docs/spike.md` с командами и выводами.

**Этап 1. Core + тесты.** Все golden-тесты паритета зелёные, битые ссылки дают понятные ошибки.

**Этап 2. Служба: Xray, TUN, маршруты.** `on`/`off` через временный отладочный вход; переключение Wi-Fi ↔ кабель не рвёт туннель надолго; после `off` таблица маршрутов как до `on`.

**Этап 3. Kill-switch и DNS.** `taskkill /f xray.exe` → интернета нет, пока туннель не поднимется; утечек DNS нет (проверка dnsleaktest-подобным запросом и захватом трафика на физическом интерфейсе); `doctor` снимает фильтры.

**Этап 4. IPC + CLI.** Все команды из 3.5; пользователь без прав администратора управляет туннелем; чужой пользователь — нет.

**Этап 5. Трей и окно.** Состояние обновляется по событиям, без опроса.

**Этап 6. Установщик и CI.** Чистая установка через `trust.ps1`, обновление поверх (настройки и сертификат на месте), удаление с ответом «Да» и «Нет» и тихое удаление — на свежем снимке виртуалки; после удаления сертификата нет в `Root` и `TrustedPublisher`. Релиз по тегу выкладывает `.exe` и `sha256`.

**Этап 7. Сервис-команды.** `test`, `doctor` (включая проверку времени), `update-core` с откатом, `self-update` со сверкой подписи, режим captive portal, `rescue.ps1` снимает фильтры на машине без установленной программы, логи с ротацией, секреты не попадают в вывод.

## 5. Стенд: агент на Ubuntu, Windows в виртуалке

Агент работает на хосте с Ubuntu и сам создаёт и ведёт тестовую виртуалку
Windows (KVM/libvirt). Ключевое свойство: **сеть агента от тестов не
зависит.** Сломанные маршруты или kill-switch отрезают только виртуалку, а
агент снаружи всегда может её спасти или откатить.

### 5.1 Что делает владелец (один раз)

У агента есть passwordless sudo на хосте (`NOPASSWD:ALL`, настроено владельцем
через `/etc/sudoers.d/`, см. 5.8) — установку пакетов, группы и проверку
`virsh` агент теперь выполняет сам:

```sh
egrep -c '(vmx|svm)' /proc/cpuinfo        # > 0, виртуализация включена в BIOS
sudo apt install qemu-kvm libvirt-daemon-system virtinst genisoimage ovmf swtpm
sudo usermod -aG libvirt,kvm $USER        # затем перелогиниться
virsh -c qemu:///system list              # должно работать без sudo
```

Владелец вручную делает только то, что требует браузера/интерактивного входа
или является его личным решением:

- скачивает ISO Windows 10 22H2 x64 с сайта Microsoft и кладёт в `~/vm-iso/win10.iso` (страница Microsoft требует ручных шагов, автоматически не скачивается);
- ставит .NET 10 SDK на хост (или поручает агенту через `dotnet-install.sh` — на усмотрение);
- проверяет, не заворачивает ли Linux-клиент vless-tunnel на хосте трафик виртуалки (NAT через `virbr0`) в свой туннель. Если заворачивает — отключить на время тестов или учитывать «туннель в туннеле» при оценке результатов. Записать вывод в раздел «Статус».

### 5.2 Параметры виртуалки

| Что | Значение |
|---|---|
| Имя | `vt-win10` |
| ОС | Windows 10 22H2 x64 (Windows 11 — позже, отдельной машиной) |
| Прошивка | BIOS (SeaBIOS) — ради внутренних снимков qcow2; UEFI + TPM нужны только для Windows 11 и усложняют снимки |
| Ресурсы | 4 vCPU, 8 ГБ RAM, диск qcow2 64 ГБ |
| Сеть | libvirt `default` (NAT, `virbr0`) |
| Драйверы и guest agent | ISO virtio-win (агент скачивает сам с fedorapeople.org, сверяет контрольную сумму) |
| Установка | без участия человека: `autounattend.xml` на отдельном ISO |

Секреты стенда (пароль администратора виртуалки, SSH-ключ) — в
`~/.config/vless-tunnel-dev/`, не в репозитории. Пароль генерируется при
создании.

`autounattend.xml` и скрипт первого входа (`setup-guest.ps1`) должны:
- создать локальную учётку администратора; автологин — постоянный (по решению владельца: это стенд для разработки, а не конечный продукт, вводить пароль на консоли каждый раз неудобно). Технически это ещё и единственный работающий способ запустить `setup-guest.ps1` без участия человека в этом образе: `Microsoft-Windows-Deployment`/`RunSynchronousCommand` не поддерживается этой сборкой Windows ни в `specialize`, ни в `oobeSystem` (проверено эмпирически через `setupact.log`), поэтому используется `FirstLogonCommands`, а для него нужен хотя бы один вход;
- поставить драйверы virtio и **qemu-guest-agent** с ISO virtio-win;
- включить **OpenSSH Server**, PowerShell как оболочку по умолчанию, вход по ключу (`administrators_authorized_keys` с правильным ACL);
- отключить сон и гибернацию (иначе автоматические тесты будут прерываться простоем) — но **не** Windows Update: владелец настоял, что стенд должен вести себя как обычная машина пользователя, иначе часть реальных проблем (обновление посреди теста, перезагрузка, столкновение с туннелем) просто не всплывёт до релиза;
- исключить `C:\dev` из проверки Defender (только эта папка со скриптами стенда, не сам vless-tunnel — тот ставится в `%ProgramFiles%\vless-tunnel\` и остаётся под обычной проверкой антивируса, как и должно быть);
- создать `C:\dev\{logs,secrets,bin}`;
- в конце выключить машину — это сигнал хосту, что установка завершена.

### 5.3 Файлы стенда в репозитории

```
vm/
  create-vm.sh          создать vt-win10 с нуля (идемпотентно: есть — не трогать)
  autounattend.xml      шаблон, пароль и ключ подставляются при сборке ISO
  setup-guest.ps1       первичная настройка Windows
  vmctl.sh              ssh | scp | exec (через guest agent) | ip | snapshot | revert | rescue | status
  with-rescue.sh        обёртка опасного теста (5.5)
```

`vmctl.sh` — единственная точка управления: агент не пишет длинные
`virsh`/`ssh` вручную. IP виртуалки — через `virsh domifaddr` или guest agent.

Выполнение команды через guest agent (работает без сети внутри виртуалки):

```sh
virsh qemu-agent-command vt-win10 '{"execute":"guest-exec","arguments":{
  "path":"powershell.exe",
  "arg":["-NoProfile","-ExecutionPolicy","Bypass","-File","C:\\dev\\rescue.ps1"],
  "capture-output":true}}'
# → {"return":{"pid":N}}
virsh qemu-agent-command vt-win10 '{"execute":"guest-exec-status","arguments":{"pid":N}}'
# вывод приходит в base64
```

### 5.4 Снимки

- `clean` — сразу после установки и настройки. **Никогда не удалять.**
- `stage-N` — перед началом каждого этапа.
- `pre-<тест>` — перед каждым опасным тестом; старые `pre-*` агент удаляет сам, оставляя последние 3.

Агент откатывает снимки сам. Откат к `clean` — только если текущий снимок
этапа тоже испорчен; записать причину в «Статус».

### 5.5 Опасные тесты и спасение

Опасный тест — всё, что меняет маршруты, DNS, брандмауэр/WFP или запускает
туннель внутри виртуалки.

**`rescue.ps1`** (внутри виртуалки, первый артефакт этапа 0) —
идемпотентный, не зависит от программы, снимает всё: службу и `xray.exe`,
маршруты и адрес TUN, DNS интерфейсов, WFP-фильтры по GUID (3.9) и правила
брандмауэра по группе, задачу `vt-rescue`. Пишет в
`C:\dev\logs\rescue-<время>.log`, что именно снял.

**`run-test.ps1`** (внутри виртуалки) — один скрипт на тест: применить →
проверить → записать `RESULT: PASS/FAIL` в лог → откатить в `finally`:

```powershell
param([Parameter(Mandatory)][string]$Name, [Parameter(Mandatory)][string]$Script)
$log = "C:\dev\logs\$Name-$(Get-Date -f yyyyMMdd-HHmmss).log"
Start-Transcript $log
try     { & $Script }                       # печатает RESULT: ...
catch   { "RESULT: ERROR $_" }
finally { & C:\dev\rescue.ps1; Stop-Transcript }
```

Проверки связи — всегда с таймаутом (`curl.exe -s --max-time 10 …`).
Тесты, где сеть **должна** пропасть (kill-switch), устроены так же: убить
Xray → убедиться, что `curl` **не** проходит → записать → откатить.

**`with-rescue.sh`** (на хосте) — обёртка, через которую агент запускает
любой опасный тест. Цепочка спасения:

1. снимок `pre-<тест>`;
2. внутри виртуалки ставится задача `vt-rescue` (через 10 минут сама запускает `rescue.ps1`; около полуночи задавать дату `/SD`);
3. `run-test.ps1` запускается через SSH под `timeout`; лог копируется на хост в `logs/vm/`;
4. проверка: SSH отвечает и из виртуалки есть интернет (`curl` без туннеля);
5. если SSH не отвечает → `rescue.ps1` через **guest agent**, ждать до 60 с, проверить снова;
6. если guest agent не отвечает или сеть не вернулась → `virsh snapshot-revert pre-<тест>`, отметить тест как `BROKE_VM`;
7. при успехе — снять задачу `vt-rescue`.

Логи — единственный источник правды о том, что происходило без связи:
результат пишется **до** отката, при неудаче агент начинает с чтения лога, а
не с повторного запуска.

Доступ с хоста при включённом kill-switch: подсеть `virbr0` — частная и
разрешена правилами (3.3), ответы на входящий SSH не блокируются. В режиме
`--proxy-lan` SSH может пропасть — это ожидаемо, спасение через guest agent.

### 5.6 Сборка и доставка на стенд

- C#-проекты собираются на хосте (`EnableWindowsTargeting=true`), юнит-тесты Core запускаются тоже на хосте;
- артефакты копируются в `C:\dev\bin` через `vmctl.sh scp`;
- установщик Inno Setup компилируется внутри виртуалки (Inno Setup ставится туда тихо) — для разработки; релизная сборка — в GitHub Actions;
- тестовая ссылка (отдельный UUID на сервере, не основной) лежит на хосте в `~/.config/vless-tunnel-dev/test-link.txt`, копируется в `C:\dev\secrets\` и в логи не попадает.

### 5.7 Golden-тесты паритета

Агент сам генерирует эталонные JSON на хосте из Linux-бэкенда
(`~/src/vless-tunnel`, подкоманда `make`), коммитит в `tests/parity/` вместе
со списком ссылок и версией эталона. Реальные UUID и ключи в эталонах
заменяются тестовыми.

### 5.8 Границы агента

- на хосте: работать только в каталоге репозитория, `~/src/vless-tunnel` (только чтение), `~/vm-iso`, `~/.local/share/vt-vm/` (диски, ISO сборки) и `~/.config/vless-tunnel-dev/`; passwordless sudo (`NOPASSWD:ALL`) есть, но использовать только для настройки стенда (пакеты, группы, libvirt/virsh), не для действий вне этих каталогов и не для операций с виртуалкой в обход `with-rescue.sh`;
- libvirt: трогать только домен `vt-win10` и его снимки; сеть `default` не менять;
- в виртуалке: права администратора, работа в `C:\dev`;
- GitHub: токен только на этот репозиторий.

### 5.9 Статус

После каждого этапа агент обновляет раздел «Статус» в конце файла: что
сделано, что проверено (со ссылкой на лог), что не получилось, какой снимок
актуален, следующий шаг. Новая сессия начинает с него.

     внешние кавычки ломали синтаксис, `sc.exe` получал испорченную
     строку. Хуже того, `Exec(...)` не проверял `ResultCode`, поэтому
     установщик рапортовал об успехе, а служба просто не появлялась —
     это не поймать иначе как проверкой `sc query` после живой
     установки. Исправлено на правильный Windows-формат
     (`binPath= "\"C:\...\App.exe\" service"` — внешние кавычки на весь
     аргумент, внутренние \"…\" на сам путь к exe, как в документации
     Microsoft) и добавлена проверка `ResultCode` с жёстким падением
     установки при ошибке `sc create`, чтобы такая поломка больше не
     проходила молча.
  2. **Ссылка на сервер не переживала ДАЖЕ обычный перезапуск службы**,
     не говоря уже об обновлении поставщиком — `TunnelController`
     держал распарсенную ссылку только в памяти процесса, нигде не
     сохранял. Это не баг конкретно установщика, а отсутствующая
     фича, которую критерий приёмки этапа 6 ("обновление поверх —
     настройки на месте") сделал видимой первым же тестом. У
     Linux-версии есть `ETC_DIR/config.json` для этого же — у Windows
     не было ничего. Добавлено: `TunnelController` теперь пишет сырой
     текст ссылки в `link.txt` рядом с `config-service.json` (то есть
     в `%ProgramData%\vless-tunnel`) при каждом успешном `set-link` и
     пытается загрузить его при старте — если файла нет или он не
     парсится, тихо остаётся в состоянии "ссылка не задана", ошибка
     только в лог.
- **Подтверждено живьём, все критерии приёмки этапа 6 (кроме подписи):**
  чистая установка регистрирует и сразу запускает службу
  (`sc query` → RUNNING), обновление поверх останавливает-заменяет-
  перезапускает без потери настроек, автозапуск-ярлыки (Пуск и
  `CommonStartup`) создаются, удаление с «Нет» оставляет `link.txt` и
  он подхватывается при следующей установке (ровно то, что обещает
  текст диалога), удаление с «Да» стирает `%ProgramData%\vless-tunnel`
  целиком, тихое удаление (`/VERYSILENT`) ведёт себя как «Нет» без
  вопроса — тоже по плану ("тихое удаление настройку сохраняет").
- **Не проверено и не могло быть проверено в этом проходе** (нет
  настоящего сертификата): реальная подпись установщика/деинсталлятора
  через `signtool`, `trust.ps1` целиком (сверка отпечатка, установка в
  `Root`/`TrustedPublisher`, снятие метки "из интернета"), удаление

  соответствующие шаги в `[UninstallRun]` корректно пропускаются, но
  живьём с непустым значением не гонялись).
- **`.github/workflows/build.yml` на самом деле уже гонялся живьём на
  GitHub Actions** — оказалось, при каждом пуше в `master` (обычный
  `on: push`), а не только по запросу, и **падал на КАЖДОМ прогоне** с

  invalid`, что нашлась вживую на стенде: директива в `[Setup]`
  безусловная, а её обязательная пара `/Ssigntool=...` кладётся в

## Этап 3.9/7: `sc failure` и проверка часов в `doctor`

Два пропуска из раздела 3.9 плана, замеченных при повторном чтении уже
после того, как основной цикл установщика был подтверждён живьём.

- **`sc failure`.** Служба регистрировалась установщиком без действий
  при сбое — падение процесса (необработанное исключение и т.п.)
  оставляло туннель выключенным до ручного вмешательства, а с
  включённым kill-switch — без интернета вовсе, до перезапуска
  вручную. Добавлен вызов `sc failure ... reset= 86400 actions=
  restart/5000/restart/30000/restart/60000` в `InstallOrUpdateService`
  (и на create, и на update — идемпотентно). **Проверено живьём**:
  `sc qfailure vless-tunnel` после установки подтверждает все три
  действия и период сброса счётчика.
- **Проверка часов в `doctor`.** REALITY и TLS ломаются при сбитых
  часах (частое дело в виртуалках) — `doctor` не предупреждал об
  этом вовсе. Добавлен `VlessTunnel.Core.ClockCheck` — сверяет
  локальное UTC-время с заголовком `Date` от `https://
  www.cloudflare.com/` (не отдельный NTP-клиент — незачем ещё один
  протокол/порт ради одной проверки, когда HTTPS:443 и так нужен
  остальному приложению), с грубой компенсацией сетевой задержки
  (половина RTT). Порог предупреждения — 5 минут (REALITY/TLS обычно
  переживают секунды-десятки секунд расхождения, ломаются на
  минутах). Подключено в обоих местах, где есть `doctor`: standalone
  (`VlessTunnel.Service.exe doctor`, без службы) и IPC-команда
  (`IpcResponse.DoctorClockSkewSeconds`/`DoctorClockError`, печатает
  CLI). 4 юнит-теста на подставном `HttpMessageHandler` (без реальной
  сети — детерминированно и быстро, как остальные тесты репозитория).
  **Проверено живьём обоими путями** (CLI через IPC и standalone) — в
  норме печатает "в порядке", после `Set-Date` вперёд на 3 часа
  корректно предупреждает о расхождении ~10800 с; часы возвращены
  на стенде обратно сразу после проверки.

  результат и с ними, и без; сам DNS-таймаут — отдельная, не

- **Итог, проверено на стенде реальным `ISCC.exe`**: установщик
