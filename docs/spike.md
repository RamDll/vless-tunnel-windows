# Этап 0б — спайк: результаты и находки

Дата: 2026-09-18 (ночная сессия). Стенд: `vt-win10`, снимок `clean`.
Тестовая ссылка: `~/.config/vless-tunnel-dev/test-link.txt` (PQ REALITY + xhttp).
Ядро: Xray-core v26.3.27 (`vm/pinned-versions.txt`, sha256 подтверждён издателем).

## Как воспроизвести

Всё через `vm/with-rescue.sh <имя> <локальный .ps1>` — эти скрипты меняют
маршруты, поэтому не запускать в обход обёртки. Артефакты xray скопированы
на VM в `C:\dev\bin\xray\` через `vmctl.sh scp`.

Способ запустить `xray.exe` так, чтобы он пережил закрытие SSH-сессии —
**обязательно через WMI**, не через `Start-Process`/`Start-Job`:

```powershell
Invoke-CimMethod -ClassName Win32_Process -MethodName Create -Arguments @{
    CommandLine = "C:\dev\bin\xray\xray.exe -config C:\dev\bin\xray\config.json"
    CurrentDirectory = "C:\dev\bin\xray"
}
```

`Start-Process`/`Start-Job`, запущенные внутри SSH-команды, умирают вместе с
сессией (Windows OpenSSH привязывает дочерние процессы к Job Object сессии
с kill-on-close) — процесс просто исчезает без ошибки, выглядит как «сам
завершился». Это отдельная находка, независимая от TUN.

## ✅ Подтверждено

1. **`xray.exe` + `wintun.dll` + TUN-инбаунд поднимают адаптер.**
   Формат `inbounds[].protocol: "tun"` угадан с первого раза и принят
   (`xray.exe -test` подтвердил, затем боевой запуск создал адаптер
   `xray0`, Status=Up, MediaConnectionState=Connected). Рабочий
   `settings`:
   ```json
   {
     "address": ["172.19.0.1/30"],
     "mtu": 1400,
     "autoRoute": false,
     "strictRoute": false,
     "stack": "gvisor",
     "endpointIndependentNat": false
   }
   ```
   `stack: "system"` тоже принимается и ведёт себя идентично (см. ниже) —
   разницы в поведении не обнаружено.

2. **Адрес НЕ назначается сам** — подтверждает архитектуру плана (3.2):
   `address` в конфиге не привязывает IP к адаптеру, это остаётся заботой
   службы (`New-NetIPAddress` вручную).

3. **Адаптер появляется в `Get-NetAdapter` РАНЬШЕ, чем готов** — сразу
   после создания `Status` пустой, а не `Up`. Ждать нужно именно
   `Status -eq 'Up'`, не просто существования объекта — иначе
   `New-NetIPAddress` падает с «Элемент не найден». Это ровно то, о чём
   предупреждал план (3.2: «дождаться адаптера... таймаут») — подтверждено
   эмпирически, будущий Service должен опрашивать статус, не только имя.

4. **Ручная настройка маршрутов (как их будет делать Service) работает
   технически корректно**: хост-маршрут до IP сервера через физический
   шлюз (анти-петля) + `0.0.0.0/1`/`128.0.0.0/1` через TUN. Таблица
   маршрутов после настройки ровно такая, как расписано в плане:
   ```
   128.0.0.0/1  0.0.0.0        xray0    metric 256
   0.0.0.0/1    0.0.0.0        xray0    metric 256
   0.0.0.0/0    192.168.122.1  Ethernet metric 0
   ```
   Прямое TCP-подключение к самому серверу (130.17.21.198:443) через
   физический маршрут — проходит успешно (анти-петлевой маршрут работает).

## ✅ Дополнительно подтверждено (после ночи): сквозной трафик работает

Ночная находка «трафик не доходит до xray через TUN» **оказалась
артефактом тестового скрипта, а не реальной проблемой**. Настоящая
причина: маршрут добавлялся (`New-NetRoute`) и тут же, в той же
PowerShell-сессии, в течение миллисекунд проверялся TCP-подключением —
Windows не успевала применить новый маршрут к движку форвардинга. Стоило
развести «добавить маршруты» и «проверить соединение» на два отдельных
вызова (естественный разрыв по времени, как и будет в реальности у
Service) — TCP до 1.1.1.1:443 через `0.0.0.0/1` → `xray0` прошёл
(`Connected=True`), и лог `xray-error.log` это подтвердил построчно:

```
[Info] proxy/tun: processing from tcp:172.19.0.1:57697 to tcp:1.1.1.1:443
[Info] app/dispatcher: taking detour [proxy] for [tcp:1.1.1.1:443]
[Info] transport/internet/splithttp: XHTTP is dialing to tcp:130.17.21.198:443, ... host www.sap.com
[Info] proxy/vless/outbound: tunneling request to tcp:1.1.1.1:443 via 130.17.21.198:443
```

Это **настоящая тестовая ссылка** (PQ REALITY + xhttp + vision,
`~/.config/vless-tunnel-dev/test-link.txt`) — то есть пункт плана
«тестовая ссылка с PQ-параметрами работает» тоже подтверждён: `xray`
успешно продолжает REALITY-хендшейк (видны `XtlsPadding`/
`XtlsFilterTls` — признаки Vision-протокола) и реально проксирует трафик
через 130.17.21.198.

Побочные (ложные) гипотезы по пути, отброшенные экспериментом, но
интересные сами по себе:
- `NdisMedium = MBB` у адаптера `wintun.sys`/Xray (виден в захвате
  `pktmon`) — реальный факт (подтверждён issue
  [XTLS/Xray-core#6019](https://github.com/XTLS/Xray-core/issues/6019):
  Xray TUN не распознаётся Windows как Remote Access Interface, в
  отличие от sing-box), но он **не мешает** передаче трафика — это
  ограничивает только удобство написания правил брандмауэра по типу
  интерфейса, не саму связность. Учесть при выборе механизма
  kill-switch (3.9/3.3): фильтровать по имени/GUID адаптера, не по типу
  интерфейса.
- `autoRoute: true` у Xray — тоже прогонялся как эксперимент, добавляет
  маршруты только для link-local/broadcast-диапазонов самой подсети
  TUN, **не** ставит общий default-through-tun маршрут — для нашей
  архитектуры (маршруты ставит Service, не Xray) не подходит и не
  нужен, `autoRoute: false` — правильный выбор с самого начала.

**Вывод для Service (этап 2):** после `CreateIpForwardEntry2`
(добавление маршрутов) нужна **пауза или проверка готовности** перед
тем, как считать туннель поднятым — например, короткий retry-цикл
пробного подключения (то же, что и «дождаться адаптера» в 3.2, только
для маршрутов). Синхронный код, который сразу после установки маршрутов
ожидает трафика в той же функции без паузы, будет ошибочно считать
туннель нерабочим.

## ✅ IPv6 через TUN с ULA-адресом

Подтверждено (план, 3.2: "для IPv6 — ULA из `fd00::/8`, без
маршрутизируемого адреса IPv6 через TUN не пойдёт"): назначил
`fd00::1/64` на `xray0`, маршруты `::/1` и `8000::/1` через TUN — TCP до
`2606:4700:4700::1111:443` (IPv6 Cloudflare) прошёл, лог Xray
подтвердил проксирование через настоящий сервер:
```
processing from tcp:[fd00::1]:65446 to tcp:[2606:4700:4700::1111]:443
tunneling request to tcp:[2606:4700:4700::1111]:443 via 130.17.21.198:443
```
IPv4 и IPv6 работали параллельно на одном запущенном `xray.exe`, без
конфликтов.

**Грабли теста (не сети):** `New-Object System.Net.Sockets.TcpClient()`
без параметров в .NET по умолчанию создаётся с `AddressFamily.
InterNetwork` (IPv4-only) — попытка `ConnectAsync` на IPv6-адрес падает
с ошибкой несоответствия семейства адресов сокета, выглядит как сетевая
проблема, а на деле нужно было `TcpClient(AddressFamily.
InterNetworkV6)`.

## ✅ `taskkill xray.exe` без kill-switch — утечка подтверждена

Ровно как предсказано планом (3.3: «На Windows — нет [kill-switch по
построению]: если Xray упал, адаптер TUN исчезает вместе с маршрутами, и
трафик молча уходит напрямую»):

1. До: TCP к 1.1.1.1:443 идёт через туннель (`Before: True`).
2. `taskkill /f /im xray.exe`.
3. Адаптер `xray0` и маршруты `0.0.0.0/1` исчезают сами (снимок
   `Get-NetAdapter`/`Get-NetRoute` сразу после — пусто).
4. После: TCP к 1.1.1.1:443 **снова проходит** (`After: True`), но уже
   напрямую через физический интерфейс — **утечка подтверждена**, без
   kill-switch туннель не даёт вообще никакой защиты в момент падения.

Подтверждает: kill-switch — часть MVP, не опция (3.3), делать
обязательно, полагаться на «TUN просто исчезнет и всё остановится» нельзя.

## ✅ Выбор механизма kill-switch: WFP (решение подтверждено)

План (3.3) изначально предполагал WFP, с альтернативой в виде правил
брандмауэра Windows (3.9, «выбор сделать на этапе 0»). После спайка
решение — **WFP**, без изменений:

- WFP работает на уровень ниже Windows Firewall API — переживает замену
  брандмауэра сторонним антивирусом (ровно тот риск, который план и
  называл слабостью правил брандмауэра, 3.9).
- Постоянные (не dynamic) WFP-фильтры переживают падение службы —
  требование плана (3.3), у обычных правил брандмауэра такого свойства
  нет само по себе (Remove-NetFirewallRule снимает их так же легко, как
  и создаёт).
- Найденное сегодня ограничение (Xray TUN не распознаётся Windows как
  Remote Access Interface, XTLS/Xray-core#6019) касается ТОЛЬКО удобной
  короткой формы правил «по типу интерфейса» — что для WFP, что для
  обычных правил брандмауэра всё равно придётся фильтровать по
  GUID/имени адаптера явно, так что это ограничение не даёт брандмауэру
  преимущества и не является аргументом против WFP.
- `rescue.ps1` уже реализован в расчёте на WFP как основной путь (снятие
  фильтров по фиксированным GUID из `vm/pinned-versions.txt`) с
  best-effort поддержкой и firewall-group как страховочного варианта —
  менять код стенда не требуется.

## ✅ MTU

Ориентир плана (1400) подтверждён реальной передачей данных, не только
handshake'ом: скачивание 3 МБ (`curl.exe` → `https://speed.cloudflare.com`,
через туннель) — `HTTP:200 size:3000000 time:0.94s speed:3.17MB/s`, без
зависаний/обрывов. Лог Xray подтверждает реальные данные (`Xtls
Unpadding`, блоки по ~4 КБ). MTU=1400 — рабочее значение, фрагментации
не обнаружено.

## ✅ / ⚠️ Смена кабель↔Wi-Fi, сон/гибернация — частично, с честной оговоркой

**Отключение/включение физического адаптера (`Disable-NetAdapter`/
`Enable-NetAdapter` на `Ethernet`) при поднятом туннеле:**
- SSH-сессия рвётся вместе с адаптером (ожидаемо — SSH тоже идёт через
  физический интерфейс, не через TUN) — тест пришлось вести через
  `vmctl.sh exec` (guest agent), а не `ssh`, он не зависит от сети.
- После обратного включения — **DHCP сам восстановил default-route,
  анти-петлевой хост-маршрут и `0.0.0.0/1` через `xray0` остались на
  месте без вмешательства**, туннель продолжил работать
  (`After: True`, проверено новым TCP-подключением к 1.1.1.1:443).

**Честное ограничение теста:** в этой VM один физический адаптер
(`Ethernet`, всегда `ifIndex=4`) — отключение/включение НЕ меняет ни
индекс интерфейса, ни адрес шлюза, поэтому это не полноценная проверка
сценария «Wi-Fi ↔ кабель» из плана (3.2: «Индекс интерфейса меняется
при каждом запуске Xray... отслеживать `NotifyRouteChange2`/
`NotifyIpInterfaceChange`... пересчитать физический шлюз и переставить
хост-маршрут»). Тест подтверждает только «адаптер мигнул, но не исчез
и не сменился» — сценарий с ДЕЙСТВИТЕЛЬНОЙ сменой интерфейса (другой
ifIndex/другой шлюз, как при физическом переключении Wi-Fi↔Ethernet)
нужно тестировать на реальном железе с двумя интерфейсами (этап 2,
возможно вторая машина стенда с Windows 11, план 5.2/6 вопрос 7).

**Сон/гибернация — не тестировалось.** VM на KVM не эмулирует
ACPI S3/S4 сон так же, как реальное железо (гостевая ОС может решить,
что "спит", но состояние QEMU-процесса и виртуальных устройств ведёт
себя иначе, результат теста был бы не показательным). Честно
откладываю на этап 2 — тестировать на реальном железе или через
`rundll32.exe powrprof.dll,SetSuspendState` с осторожной проверкой,
что даёт именно VM в libvirt, отдельным экспериментом, не в рамках
этой ночи.
