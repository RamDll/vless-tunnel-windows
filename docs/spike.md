# Этап 0б — спайк: результаты и находки

Дата: 2026-09-18 (ночная сессия). Стенд: `vt-win10`, снимок `clean`.
Тестовая ссылка: `~/.config/vless-tunnel-dev/test-link.txt` (PQ REALITY + xhttp).
Ядро: Xray-core v26.3.27 (`vm/pinned-versions.txt`, sha256 подтверждён издателем).

## Как воспроизвести

Всё через `vm/with-rescue.sh <имя> <локальный .ps1>` — эти скрипты меняют
маршруты, поэтому не запускать в обход обёртки. Артефакты xray скопированы
на VM в `C:\dev\bin\xray\` через `vmctl.sh scp`.

Способ запустить `xray.exe` так, чтобы он пережил закрытие SSH-сессии —
**обязательно через WMI**, не через `Start-Process`/`Start-Job`:

```powershell
Invoke-CimMethod -ClassName Win32_Process -MethodName Create -Arguments @{
    CommandLine = "C:\dev\bin\xray\xray.exe -config C:\dev\bin\xray\config.json"
    CurrentDirectory = "C:\dev\bin\xray"
}
```

`Start-Process`/`Start-Job`, запущенные внутри SSH-команды, умирают вместе с
сессией (Windows OpenSSH привязывает дочерние процессы к Job Object сессии
с kill-on-close) — процесс просто исчезает без ошибки, выглядит как «сам
завершился». Это отдельная находка, независимая от TUN.

## ✅ Подтверждено

1. **`xray.exe` + `wintun.dll` + TUN-инбаунд поднимают адаптер.**
   Формат `inbounds[].protocol: "tun"` угадан с первого раза и принят
   (`xray.exe -test` подтвердил, затем боевой запуск создал адаптер
   `xray0`, Status=Up, MediaConnectionState=Connected). Рабочий
   `settings`:
   ```json
   {
     "address": ["172.19.0.1/30"],
     "mtu": 1400,
     "autoRoute": false,
     "strictRoute": false,
     "stack": "gvisor",
     "endpointIndependentNat": false
   }
   ```
   `stack: "system"` тоже принимается и ведёт себя идентично (см. ниже) —
   разницы в поведении не обнаружено.

2. **Адрес НЕ назначается сам** — подтверждает архитектуру плана (3.2):
   `address` в конфиге не привязывает IP к адаптеру, это остаётся заботой
   службы (`New-NetIPAddress` вручную).

3. **Адаптер появляется в `Get-NetAdapter` РАНЬШЕ, чем готов** — сразу
   после создания `Status` пустой, а не `Up`. Ждать нужно именно
   `Status -eq 'Up'`, не просто существования объекта — иначе
   `New-NetIPAddress` падает с «Элемент не найден». Это ровно то, о чём
   предупреждал план (3.2: «дождаться адаптера... таймаут») — подтверждено
   эмпирически, будущий Service должен опрашивать статус, не только имя.

4. **Ручная настройка маршрутов (как их будет делать Service) работает
   технически корректно**: хост-маршрут до IP сервера через физический
   шлюз (анти-петля) + `0.0.0.0/1`/`128.0.0.0/1` через TUN. Таблица
   маршрутов после настройки ровно такая, как расписано в плане:
   ```
   128.0.0.0/1  0.0.0.0        xray0    metric 256
   0.0.0.0/1    0.0.0.0        xray0    metric 256
   0.0.0.0/0    192.168.122.1  Ethernet metric 0
   ```
   Прямое TCP-подключение к самому серверу (130.17.21.198:443) через
   физический маршрут — проходит успешно (анти-петлевой маршрут работает).

## ❌ Не подтверждено — открытый вопрос на день

**Трафик не доходит до xray через TUN.** TCP-подключение к 1.1.1.1:443
(через `0.0.0.0/1` → `xray0`) стабильно висит до таймаута
(`WSAETIMEDOUT`), при этом:
- маршруты в таблице корректны (см. выше), адаптер `Up`/`Connected` —
  проверено прямо в момент теста, не постфактум;
- `xray`-лог (`access.log`/`error.log`, `loglevel: debug`) **пустой**,
  кроме строки `Logger started` — то есть до Xray пакеты не долетают
  вообще, это не проблема REALITY/маршрутизации внутри Xray;
- смена `stack: gvisor` → `stack: system` ничего не изменила — проблема
  не в конкретной реализации TUN-стека Xray;
- `Test-NetConnection`/`Find-NetRoute` в non-elevated SSH-сессии либо
  требуют admin (ICMP raw socket), либо тихо возвращают пусто без
  ошибки — не показательны в этом окружении, пришлось перейти на чистый
  `System.Net.Sockets.TcpClient` и прямой `Get-NetRoute`.

**Гипотезы, не проверенные из-за времени (продолжить утром):**
- Захват пакетов (`netsh trace start capture=yes` или аналог) на
  интерфейсе `xray0` и на физическом — увидеть, уходит ли пакет с TUN
  вообще, или он гасится раньше (Windows Filtering Platform по
  умолчанию, профиль сети адаптера классифицирован как Public и т.п.).
- Проверить `Get-NetConnectionProfile` для `xray0` — если профиль
  Public, часть правил брандмауэра Windows по умолчанию может резать
  исходящий трафик нестандартных адаптеров агрессивнее, чем кажется.
- Попробовать без REALITY/PQ вообще (голый TCP outbound на публичный
  сервер) — отделить «TUN не работает в принципе» от «TUN работает, но
  что-то не так конкретно с этим outbound/конфигом».
- Проверить версию xray на известные issue по `tun` inbound на Windows
  под vsock/nested-virtualization (мы внутри KVM/QEMU, e1000e NIC) —
  возможно, известное ограничение самого враппера wintun в этой сборке.
- Elevated-сессия вместо vtadmin non-elevated — на случай, если
  проблема тоже упирается в привилегии (хотя `xray.exe` сам создаёт
  адаптер и он видим как `Up`, что обычно требует admin и это сработало
  — так что маловероятно, но не исключено).

**Вывод:** пункт плана «ручные маршруты по 3.2 → трафик идёт через
сервер, петли нет» — выполнен только наполовину: маршруты правильные,
петли нет (прямое подключение к серверу работает через физический путь),
но сквозной проход через TUN не подтверждён. Печать с PQ-параметрами
самим Xray (REALITY-хендшейк) вообще не была протестирована, так как до
неё дело не дошло — пакеты не покидают TUN-инбаунд.
